# API v0.1

## Рабочие изменения после 0.4.1 (не опубликованы)

Новый сервер возвращает `chatProtocol: 2`, `chatFeed`, `chatToken`, `chatEphemeral`
в комнатах с E2EE и без него. Без E2EE сообщения и вложения доступны серверу;
клиент не обозначает такой чат как сквозное шифрование. Встроенная комната хранит
до 500 сообщений в памяти. Для отдельного сервера `VOICECORD_CHAT_MAX_MB`
задаёт размер SQLite-базы в МиБ (128 по умолчанию, `0` — без лимита), включая
сообщения, картинки, профили и индексы. При заполнении удаляются старейшие сообщения;
срока в семь дней и ограничения на количество сохранённых сообщений больше нет.

- `GET /api/chat?limit=100` выдаёт последние сообщения в возрастающем порядке.
  `limit` — 1–500. `before`, `after` или `around` выбирают страницу; ненулевые
  курсоры взаимоисключающие. Ответ содержит `first`, `last`, `hasOlder`, `hasNewer`,
  `messages`; `readAfter` добавляет точный `unread`. Старый запрос без `limit`
  сохраняет прежний формат. Клиент держит окно 25–500 сообщений, по умолчанию 100.
  Профили выдаются порциями до 500 по `profilesAfter`; полная порция означает,
  что клиенту следует продолжить запрос с последней полученной ревизии.
- Сообщение v2 может содержать зашифрованный конверт с текстом, краткой цитатой
  ответа и метаданными картинки. Расшифрованное тело — до 12288 байт, текст —
  до 4096 байт. `attachmentId` связывает сообщение с загруженным вложением;
  сервер проверяет владельца. Без E2EE `nonce` пустой, содержимое хранится открыто.
- `POST /api/chat/attachments/{id}` принимает до 2 МиБ + 28 байт двоичных данных
  (исходный файл + IV/tag AES-GCM в E2EE). `id` — 32 hex-символа. Повтор тех же
  байтов идемпотентен, конфликт получает 409, превышение размера — 413.
  Вложения входят в общий `VOICECORD_CHAT_MAX_MB`; на автора допускаются три
  незавершённые загрузки. Если новая загрузка не помещается даже после очистки,
  сервер возвращает 507 и откатывает удаление существующей истории. Неиспользованные
  загрузки удаляются через десять минут при следующей очистке (раз в минуту).
  Картинки удалённых по лимиту сообщений освобождаются вместе с сообщениями.
- `GET /api/chat/attachments/{id}` требует токен и существующее сообщение,
  ссылающееся на вложение. Ответ — `application/octet-stream`, `Cache-Control:
  no-store`. Ключ изображения связан с feed, а AEAD — с ID вложения. Клиент
  допускает только статические PNG/JPEG/WebP до 2 МиБ, 8192 px на сторону и
  16 мегапикселей. Полные изображения не входят в страницы истории.
- `GET /api/preview?readAfter=0&readFeed=...` требует `Authorization: Bearer`
  токена комнаты. Возвращает число участников, максимум три имени/профиля,
  feed и точный unread. Публичный `/api/presence` по-прежнему возвращает только
  количество: имена, профили и непрочитанные через него не раскрываются.

Ниже описан исходный API, сохранённый для совместимости.

## POST /api/connect

Заголовок `Content-Type: application/json`. Максимум 4096 байт тела. Неизвестные поля, несколько JSON-объектов, управляющие символы в никнейме отклоняются.

```json
{"nickname":"Друг","password":"общий пароль"}
```

Для комнаты с обязательным E2EE клиент добавляет `"e2ee":true` и `"e2eeKeyId":"<SHA256 raw 32-byte key>"`. Секретный ключ API не принимает. Без этих полей возвращается HTTP 426; при несовпадении с настроенным `VOICECORD_E2EE_KEY_ID` — 403. Ответ успешного входа содержит `e2eeRequired`; при обязательном режиме JWT также содержит атрибут `voicecord.e2ee=required`. Это политика клиентов, а не криптографическая проверка SFU содержимого опубликованных кадров. Подробности: [E2EE.md](E2EE.md).

`GET /api/config` возвращает публичную политику `{"e2eeRequired":true|false}` без пароля и ключей.

Никнейм: 1–32 Unicode-символа после удаления пробелов по краям. Совпадение имён допустимо. Внутренняя идентичность — случайные 128 бит на каждое подключение.

Успех, HTTP 200:

```json
{"url":"wss://203.0.113.10/rtc","token":"<JWT>","identity":"<random-id>","room":"common","expiresIn":300}
```

Токен HS256 содержит `iss`, `sub`, `name`, `nbf`, `exp` и LiveKit video grant с `roomJoin=true`, комнатой `common`, `canPublish=true`, `canSubscribe=true`, `canPublishSources=["microphone"]`, `canPublishData=true` и `canUpdateOwnMetadata=false`. Права администратора не выдаются. Начальный TTL составляет пять минут. LiveKit управляет обновлением токена установленной сессии.

Ошибки: `{"error":"сообщение"}` с HTTP 400, 401, 413/400 для большого тела, 415, 429 или 503. При превышении пяти запросов подключения с одного IP в минуту возвращается `Retry-After: 60`. Максимум четыре параллельных PBKDF2-проверки во всём процессе. После рестарта лимиты сбрасываются.

Пароли, токены и тела запросов не журналируются. Ответы имеют `Cache-Control: no-store`. CORS не открыт: API вызывается main-процессом Electron, не произвольным сайтом.

## GET /api/chat и POST /api/chat

На встроенном сервере с E2EE и на отдельном сервере с E2EE и заданным отпечатком ключа успешный вход дополнительно возвращает `chatFeed`, `chatToken` и `chatEphemeral`. Значение `chatEphemeral: true` означает, что лента хранится в памяти и очищается при остановке сервера. Токен действует 12 часов и передаётся в `Authorization: Bearer …`. Клиент обновляет его через обычный вход в API.

`GET /api/chat?after=0` возвращает `first` с первым доступным номером (0 для пустой ленты) и массив `messages` в порядке возрастания `id`. При следующем запросе клиент передаёт самый большой полученный номер в `after`. Записи содержат `id`, `author`, `sent` (Unix-время в миллисекундах), `requestId`, `nonce` и `ciphertext`. Сообщения подтверждённого профиля также содержат `authorId`.

`GET /api/config` выдаёт одноразовый `profileChallenge`, когда сервер поддерживает историю чата. Клиент передаёт в `POST /api/connect` объект `profile` с публичным ключом Ed25519 (`key`), `challenge` и `signature`. Ключ и подпись кодируются в Base64URL без дополнения. Подписывается строка `voicecord-profile-v1\n<challenge>\n<nickname>` с исходным никнеймом запроса. Ответ содержит `profileId` с SHA-256 публичного ключа, а токен чата привязан к этому ID.

`POST /api/chat/profile` обновляет никнейм подтверждённого автора и, при наличии, зашифрованный аватар. В теле передаются `nickname` и необязательные `nonce` и `ciphertext` в Base64. Чтобы получить актуальные профили вместе с сообщениями, клиент добавляет `profilesAfter=0` к первому запросу истории. Затем передаёт наибольшую полученную `revision`. Профили содержат `id`, `revision`, `nickname` и зашифрованный аватар. Новый клиент получает профиль автора даже в его отсутствие.

`POST /api/chat` принимает JSON с `requestId` (32 строчных шестнадцатеричных символа), `nonce` (12 байт в Base64) и `ciphertext` (до 4112 байт в Base64). Ответ содержит `id` сохранённого сообщения. Повтор того же пакета с тем же `requestId` возвращает исходный номер, пока запись доступна. Другой пакет с тем же `requestId` получает HTTP 409.

## GET /healthz

HTTP 200: `{"status":"ok"}`. Проверяет процесс API; не проверяет доступность LiveKit, UDP или сертификата. Для полной диагностики используйте подключение двух клиентов.

## Конфигурация API

`LISTEN_ADDR` — по умолчанию `127.0.0.1:8080`.

Обязательные `LIVEKIT_API_KEY`, `LIVEKIT_API_SECRET` (минимум 32 символа), `LIVEKIT_URL`, `VOICECORD_PASSWORD_HASH`.

Формат хеша: `pbkdf2-sha256$600000$<base64url salt 16 bytes>$<base64url SHA256 digest 32 bytes>`, без padding. Получить свой хеш можно командой `go run . hash-password`, передав пароль в stdin; configure использует тот же формат.

## GET /api/presence

Публичный агрегированный счётчик: `{"participants":2}`. Имена и идентификаторы не передаются. Сервер кэширует результат LiveKit на 10 секунд; клиент опрашивает закладки каждые 10 секунд, пока окно видно и активно. HTTP 503 означает, что количество неизвестно. Старые серверы без этого маршрута отображаются с `?`.

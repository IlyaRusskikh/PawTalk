# Совместимость опубликованных компонентов

[English](compatibility.en.md) · [Документация](../README.ru.md)

Проверенная 15 ноября 2026 года совместимая комбинация опубликованных **preview API 2**:

| Компонент | Релиз |
| --- | --- |
| Windows Client | [client-v0.12.1](https://github.com/IlyaRusskikh/PawTalk/releases/tag/client-v0.12.1) |
| Постоянный Server | [server-v0.11.1](https://github.com/IlyaRusskikh/PawTalk/releases/tag/server-v0.11.1) |
| Windows/Linux Manager | [manager-v0.5.1](https://github.com/IlyaRusskikh/PawTalk/releases/tag/manager-v0.5.1) |

Это **датированная проверенная комбинация, а не закрепление версий для установки**. Для более новых выпусков сверяйте требования в [каталоге загрузок](https://ilyarusskikh.github.io/PawTalk/downloads/) и [описаниях релизов](../../releases/README.ru.md).

API 2 требует серверный API/data schema 2 и обязательное E2EE. **Клиенты и серверы API 1 несовместимы с API 2; автоматической миграции старого членства, истории, паролей и резервных копий нет.** Старые данные сохраняйте отдельно, не импортируя их как API 2. Обновление Manager не заменяет установленный Server автоматически.

У Server и Manager собственные теги выпусков, хотя пакет Manager содержит инструменты Windows и Linux. Отдельного номера версии Manager для каждой ОС нет.

## Подготовленные исходники выпусков

Исходники выпусков [Client 0.13.0](../../releases/client-v0.13.0.ru.md) и
[Server 0.12.0](../../releases/server-v0.12.0.ru.md) сохраняют API/data schema 2.
Сначала обновляйте Server для доступа к перечисленным ниже capabilities. Manager
0.5.1 совместим и устанавливает Server отдельно; новый Server не встроен в Manager.
Эта комбинация исходников не меняет каталог опубликованных выпусков.

## Capabilities новых функций в исходном коде

API/data schema остаются равными 2; добавлены необязательные activity-v1, attachment-removal-v1, link-cancel-v1, server-avatar-v1, polls-v1, system-poll-results-v1, chat-events-v1, server-events-v1 и message-events-v1. Сначала обновляйте Server. Без capabilities основной чат/голос доступны; создание аватара/опроса скрыто, неподдерживаемое удаление вложения/отмена привязки сообщает о необходимости обновления Server. Старый Client игнорирует дополнительные поля и показывает опрос текстом вопроса без голосования. Муты уведомлений и стрелка перехода — локальные функции Client. При наличии chat-events-v1 активный чат использует аутентифицированный WebSocket; со старыми Server сохраняется опрос. API и контракты выпуска Manager не меняются.

В базы API 2 добавляются отдельные таблицы без переписывания идентичностей и прежних таблиц; это не миграция API 1. См. [контракты реализации](../../architecture/chat-features.ru.md).

media-files-v1 разрешает зашифрованные вложения до 50 МБ; старые Server API 2 сохраняют лимит 2 МБ. checklists-v1 включает создание, редактирование и отметки списков. Старые Client показывают названия списков, игнорируя дополнительные зашифрованные поля; просмотр новых вложений там отсутствует. Для всех функций обновите Server перед Client. Контракты Manager не изменены.

Необязательная capability checklist-events-v1 передаёт версии отметок через существующий WebSocket сообщений. На старых Server Client сохраняет резервный опрос.

`media-gallery-v1`: до десяти зашифрованных файлов с готовыми кадрами видео, не более двадцати уникальных ID вложений на сообщение. Новый Client проверяет capability перед отправкой галереи; старые сообщения с одним файлом поддерживаются. Старый Client нужно обновить для просмотра галерей. Версии API/data и миграции Manager не меняются.

Для демонстрации экрана в постоянной комнате нужны Client 0.16.0 и Server 0.15.0. Client 0.16.0 также поддерживает демонстрацию в своих временных комнатах. Демонстрация использует зашифрованную комнату LiveKit в API 2 и API 3. Client публикует демонстрацию, когда сервер разрешил её в правах голоса. На старых Server доступны голос и чат. Для просмотра нескольких стримов и воспроизведения звука только выбранного стрима обновите Client зрителей. Системный звук и звук приложения передаются одним типом аудиодорожки. Старые Client могут воспроизводить её как обычный звук звонка.

## Защищённый доступ (API 3)

Manager 0.7.1 отклоняет обновления Server после перехода на API 3. Manager 0.7.2 поддерживает обновление работающей комнаты, уже переведённой на API 3, с Server 0.14.1 до опубликованного Server 0.15.0 через обычное меню обновлений. Для этого нужен подписанный выпуск 0.15.0. Комната остаётся в API 3. См. [описание Manager 0.7.2](../../releases/manager-v0.7.2.ru.md).

Server 0.14.3 и временные комнаты из Client 0.15.3 предоставляют в API 3 тот же прокси обновлений Client, что и в API 2. Старые серверы API 3 могут принимать подключения к чату и возвращать HTTP 404 для `/api/updates/`. Клиенты с поддержкой прокси смогут использовать его после обновления хоста.

В Client 0.15.2 при удалении вложения во время редактирования используется существующий API зашифрованных правок сообщения. Обновите все клиенты в комнате, чтобы они отображали такие правки. Зашифрованный оригинал остаётся частью защищённой истории, и получатели могли уже сохранить его.

Client 0.15.1 берёт цвета проверенных упоминаний ролей из необязательного поля `roleColors` в списке участников защищённого канала. В постоянных комнатах это поле передаёт Server 0.14.2. Во временных комнатах Client 0.15.1 поддержка уже включена. Старые версии используют стандартное оформление упоминаний.

Для управляемого переноса через Client требуется Server 0.14.1. В Server 0.14.0 окно переноса не может прочитать контрольную точку, подготовленную через Manager. Если комната на этой версии уже в режиме обслуживания, выполните откат в Manager, затем обновите Server и подготовьте перенос заново.

Client 0.15.0 создаёт новые временные комнаты на API 3 и по-прежнему подключается к постоянным серверам API 2. Client до 0.14.1 включительно требует API 2. Постоянный Server 0.14.0 сохраняет существующую комнату на API 2, пока владелец явно не подтвердит подготовленный переход. Для миграции на хосте используйте Manager 0.7.0. При миграции исходные данные API 2 замораживаются. Действующие баны API 2 сохраняются для эффективного профиля после переключения. Модератор с правом бана может снять их через API 3. Снятие фиксируется в подписанной политике API 3. Для повторного вступления нужна действующая ссылка.

В обновлённых Client и Server действующий участник после миграции может открыть приглашение API 3 из прежнего профиля Client на прежнем устройстве. Client подтверждает существующее членство и регистрирует ключ устройства без расходования приглашения. Роли и правила доступа сохраняются. Новые пакеты ключей публикует устройство, у которого уже есть доступ к каналу.

Новые контрольные точки миграции и временные комнаты в текущих сборках разработки используют проекцию политики v18. После переключения Client владельца, у которого сохранён ключ комнаты API 2, локально перешифровывает общий аватар при первом подходящем подключении. Добавленное позднее устройство получает свой пакет ключа от устройства, которое уже может открыть аватар. Устройство на замену может восстановить аватар через зарегистрированный резервный пакет своего профиля.

Для восстановления устройства нужны сборки Client и Server с поддержкой подписанного действия `recovery.device` и поканальных аттестаций v2. Резервный набор закрепляет тот же сервер и начальную политику при подключении с нового устройства. Более ранний Client из ветки разработки останавливает проверку политики на новом действии. Новая подготовка миграции регистрирует проверенный миграционный код в API 3. Уже подготовленные контрольные точки сохраняют прежний формат. После переключения нового переноса владелец может вставить миграционный код в настройках восстановления и экспортировать переносимый набор без замены кода.

Обновлённый Client позволяет изменить адрес сохранённого сервера API 3, даже если прежний адрес недоступен. При вводе адреса без ссылки клиент использует сохранённый отпечаток сертификата, если он есть. Если сертификат сменился, нужна актуальная ссылка на сервер с его отпечатком. Клиент проверяет идентичность и начальную политику сервера и подтверждает доступ существующего устройства, прежде чем сохранить новый адрес.

Передача владения требует поддержки подписанного действия `owner.transfer` и аттестаций v2 с идентификатором профиля подписанта. Первоначальная идентичность сервера и закреплённая начальная политика сохраняются. Более ранний Client из ветки разработки отклоняет новое действие при проверке цепочки.

Для добавления устройства к существующему защищённому профилю нужны Client и Server с поддержкой подписанного действия `device.bind`. После подтверждения прежние устройства и сессии продолжают работать. Новое устройство использует собственный ключ шифрования и может ждать доставки ключей каналов по действующим правам профиля. Все клиенты защищённого сервера должны поддерживать это действие при проверке цепочки политики.

Для связывания и отвязки существующих профилей API 3 нужно поддерживать подписанные действия `profile.link` и `profile.unlink`. Перенесённые устройства открывают сессии под выбранным основным профилем. При отвязке сессии отделённых устройств завершаются. Ранее выданные приглашения сохраняют подписанного автора и политику выпуска.

Для прямой повторной привязки отвязанного устройства нужны Client, который готовит новый ключ согласования, и Server с поддержкой подписанного разрешения и квитанции привязки. После ранней отвязки без такого разрешения возможно повторное вступление по новому приглашению. При повторной привязке применяются действующие роли выбранного основного профиля.

Новые миграции сохраняют связки профилей и происхождение устройств в подписанной начальной политике. Ранее подготовленные контрольные точки сохраняют свой формат. Подписанное действие `scope.device` позволяет владельцу передать подпись поканальных аттестаций другому действующему устройству того же профиля. После передачи текущие аттестации используют v2, в том числе после обратной передачи исходному устройству.

Проекция v9 включает параметры канала в поканальное доказательство. Для делегированного редактирования нужны проекция политики v9 или новее и поддержка `channel.settings.scoped` в Client и Server. Предыдущие версии проекции сохраняют свои правила проверки. Новые временные комнаты и регистрации получателей при миграции используют v18. Ранее подписанные политики остаются читаемыми.

Обновлённые Client и Server поддерживают проверку квитанции делегированного редактирования по подписанной операции и предыдущей аттестации. На Server без этого маршрута Client ждёт обычную аттестацию новой ревизии.

В обновлённых Client и Server право Administrator открывает проверяемые редакторы ролей, категорий и каналов. Server ограничивает выдачу полной цепочки действующим владельцем и участниками с Administrator. Сборки без этого расширения используют прежнее поведение редакторов.

`protectedExplicitAdminView` позволяет администраторам явно добавить себя и других администраторов в правила просмотра канала. Явное разрешение сохраняется, если участник позже потеряет Administrator. Перед использованием обновите Server и все клиенты API 3. Более ранние сборки Client, которые проверяют полную цепочку политики, могут отклонить изменение.

`protectedOwnRoleStyle` позволяет администраторам менять название, цвет и значок своей высшей роли. Разрешения, иерархия, группировка участников и право упоминать роль подчиняются обычной иерархии. Перед использованием обновите Server и все клиенты API 3.

Состояние сервера API 3 включает пустые категории для действующего владельца и администраторов с полным доступом к политике. Они могут создать канал прямо из категории. Остальные участники получают категории, в которых им виден хотя бы один канал.

Проекция v10 добавляет отдельное поканальное доказательство права `channel.access.edit` и применимых правил ролей. Проекция v11 добавляет доказательство ранга выбранных профилей. Проекция v12 также подтверждает, обходят ли эти профили ACL канала благодаря владению или праву `server.administrator`. Проекция v13 дополнительно закрепляет состав получателей живого поколения по профилям. Сервер открывает эти группы только исполнителю живой ротации, которому действующая аренда уже разрешает видеть полный текущий состав. Проекция v14 также закрепляет архивные группы с отдельными доменами доказательств. При поканальной архивной ротации открываются только данные архивных получателей. Проекция v15 дополнительно закрепляет группы получателей правки с ограниченной историей на позиции оригинала. Поканальное основание правки открывает только допущенных читателей, прежнее плоское доказательство сохраняется для старых ревизий. Проекция v16 добавляет обязательство о точном эффекте одиночного поканального запрета `channel.view` для роли. Задача живой ротации может раскрыть затронутые профили для подписанной правки. Для этого перехода исполнитель может проверить точный состав живых получателей по предыдущей аттестации и подписать новое живое поколение до появления следующей. Поканальный клиент проверяет хеш перехода и свой допуск перед использованием адресного живого ключа. Архивная ротация использует отдельные группы архивных получателей и сверяет источники с живой цепочкой того же изменения роли. Поканальная правка до новой аттестации подтверждает оставшихся читателей с ограниченной историей на позиции оригинала и использует публичный ключ обёртки проверенного архивного поколения. Проекция v17 закрепляет полномочия создателя приглашения, допуск и число использований. При первом вступлении ранее допущенный читатель может выпустить подписанный живой ключ до новой аттестации. При полной истории читатель архива также может опубликовать архивный ключ со связями к предыдущей архивной вершине и ещё не покрытым живым поколениям. Новичок проверяет позицию допуска к живому поколению и открывает старые сообщения через архив. Проекция v18 закрепляет полномочия назначать роли, применимые правила канала и состав получателей по подписанному назначению. Получатель ключа проверяет допуск делегата и цели по скрытому идентификатору исходного списка участников. При изменении только FullHistory клиент проверяет подписанный переход и продолжает использовать прежний живой ключ, пока архивная задача в очереди. При предпросмотре обновлённый Client запрашивает как базовую версию v10 и предлагает v18. Переход фиксируется подписанным изменением. Сохранённые доказательства v9–v17 остаются проверяемыми. Client останавливает проверку на неподдерживаемой ревизии.

Обновлённые Client и Server v17 также поддерживают общую живую ротацию для последовательных первых вступлений по цепочке подписанных квитанций от аттестованной политики. Вступления с полной историей также могут использовать общую архивную ротацию. Каждая квитанция закрепляет позицию допуска своего устройства. Ранее опубликованные поколения сохраняют подписанное основание при последующей аттестации промежуточной политики.

Обновлённые Client и Server API 3 могут согласовать выдачу отдельных поканальных доказательств ключей свыше 16 МиБ частями. При каждом продолжении сервер проверяет текущий доступ. Для задачи ротации требуется та же действующая аренда. Клиент проверяет хеш полного ответа перед разбором. Малые ответы сохраняют формат JSON.

С возможностью `protectedPollResultTasks` Server закрывает голосование в срок и ждёт обновлённого Client для отдельной публикации. Исполнитель должен читать исходный опрос и иметь готовый живой пакет. Уже опубликованные итоги сохраняют прежний формат и системную подпись.

`media-variants-v1` (API 2) и `protectedMediaVariants` (API 3 в разработке) разрешают отправку версий медиа после обновления Server. Существующие вложения читаются, а обновлённый Client отправляет в прежнем формате на Server без соответствующей возможности. Более ранний Client API 2 с поддержкой галереи открывает оригинал и пропускает дополнительные поля. В комнатах API 3 на сборках разработки принимающие Client нужно обновить перед отправкой версий медиа. Предыдущие сборки разработки распознают только прежние подписанные ссылки на вложения. Лимиты и схемы Client и Server сохраняются. См. [контракт медиа](../../architecture/chat-features.ru.md#версии-медиа).

Необязательные ширина и высота превью передаются внутри зашифрованного сообщения в обоих API. Обновлённый Client использует их при наличии, а для старых сообщений сохраняет прежнюю заглушку. Это дополнение не требует обновления Server или Manager.

Серверы API 3 с возможностью protectedEvents принимают WebSocket на /api/v3/events с закреплённым TLS и токеном сессии. Прежние клиенты получают кадры пересинхронизации, состояния, изменений чата и подтверждения работы соединения. Кадр чата указывает канал после проверки области доступа и позиции оригинала при отправке. Сервер с возможностью `protectedMessageDelivery` также принимает параметр `&delivery=1`. В таком соединении сервер может отправлять новые зашифрованные записи с текущей границей истории. Он проверяет сессию и доступ к истории в той же ограниченной по времени транзакции, в которой отправляет кадр. Клиент использует существующую проверку сообщений. История, пропуски, неподдерживаемые кадры и пересинхронизация после переподключения используют HTTP. Для прямой доставки обновите Server и Client.

При наличии `protectedPresence` обновлённый клиент API 3 сообщает об активности устройства с интервалом фонового обновления. Сервер возвращает статус «В сети», «Отошел» или «Не в сети» только для профилей, уже видимых в запрошенном списке участников. Профиль считается активным, пока активно хотя бы одно устройство. Данные устройства устаревают через 60 секунд без обновления. Прежние серверы пропускают это поле. Прежние клиенты API 3 не сообщают об активности.

Состояние API 3 может содержать `voiceParticipants` для каждого видимого голосового канала. В список входят только активные сеансы с разрешением на подключение. Сервер передаёт идентификаторы профилей, имена и идентификаторы текущих голосовых сеансов для адресной модерации. Прежние серверы пропускают список. При модерации сервер проверяет права в канале и целевой сеанс. PawTalk проверяет текущий лимит при резервировании места, поэтому изменение применяется и в занятом канале.

API 3 разрешает 1200 аутентифицированных запросов в минуту на эффективный профиль участника. Для владельца и участников с правом «Администратор» этот лимит отключён. Для публичных запросов и входа действует лимит по IP-адресу, который видит сервер. Медленный режим канала и отдельные лимиты на сообщения и одновременные соединения действуют независимо.

Первичное окно истории API 3 может содержать последнюю сохранённую позицию, доступную участнику. Клиент использует её, чтобы открыть последние сообщения. При отсутствии поля клиент может читать с первой разрешённой позиции. Среди действий голосовой модерации сервер может предложить разовое отключение. Для него сервер проверяет право `voice.move` и иерархию ролей в исходном канале. Участник может подключиться снова, если у него по-прежнему есть доступ к каналу.

Для перемещения текстовых и голосовых каналов без категории в одном списке API 3 использует `MixedOrder` в подписанном запросе политики и версию 3 подтверждения порядка. Для этой возможности обновите сервер и клиент. Старые записи политики и подтверждения порядка сохраняют исходные правила группировки и остаются проверяемыми.

`protectedVoiceControls` объявляет список участников голосовых каналов, замеры связи и серверные ограничения API 3. В списке только активные участники голосовых каналов, видимых запрашивающему. Замеры доступны участникам текущего звонка и удаляются из памяти по истечении срока. Перед применением серверных ограничений обновите все клиенты: операция добавляет подписанное изменение `Mode: "server"`, которое старые клиенты не умеют проверять.

`protectedVoiceChannelControls` включает разовое выключение микрофона и звука в канале между обновлёнными клиентами. Участник может включить их обычными кнопками управления звуком. Сохранённые ранее ограничения канала можно снять через меню модерации. Прежде чем администратор ограничит владельца или владелец либо администратор снимет с себя серверное ограничение, обновите все клиенты. Подписанные операции используют обновлённые правила проверки прав. Возможность `protectedVoiceEvents` включает уведомления для обновления состояния голосовых каналов через соединения с `&voice=1`. Старые клиенты продолжают опрашивать сервер. С возможностью `protectedVoiceMediaDeafen` обновлённые клиенты подписывают серверное отключение звука в режиме `server-media`. LiveKit запрещает участнику передавать и получать аудио, а проверенный голосовой ключ остаётся у участника. Серверный мьют и отключение звука в этом режиме сохраняют действующий ключ при прежнем составе получателей. Ранее подписанные ограничения читаются по прежним правилам и исключают участника из получателей ключа до снятия. Перед использованием нового режима обновите все клиенты.

`protectedComposerEvents` включает индикаторы набора текста и записи голоса в WebSocket с параметром `&composer=1`. Клиент отправляет временный статус через `PUT /api/v3/composer/{channel}`. Сервер проверяет право отправки и передаёт канал, идентификатор профиля и статус только тем, кто видит этот текстовый канал. Клиент убирает устаревший статус по таймеру. Для работы нужны обновлённые Client и Server.

Записи аудита API 3 могут включать имена участников, названия объектов и назначенных ролей. Клиент показывает доступные названия или обозначает тип объекта. Для проверки подписи порядка по-прежнему используются внутренние идентификаторы.

На перенесённых серверах API 3 клиент может запросить зашифрованные аватары прежних профилей с помощью `legacyAvatars=1`. Сервер выдаёт аватары только участников, видимых в запрошенном списке. Клиент использует ключ прежней комнаты, сохранённый на устройстве после миграции. Прежние версии сервера пропускают это поле. Устройства без ключа показывают инициалы.

Обновлённый Server API 3 объявляет возможности `protectedDeviceRevocation` и `protectedProfileAvatar`. Первая открывает существующее подписанное действие `device.revoke` через маршруты политики. Обновлённый Client показывает его владельцу и администраторам. Вторая добавляет зашифрованное хранение аватара с версиями и пакетами для устройств одного профиля. После привязки нового устройства клиент, у которого есть доступ к текущему аватару, публикует его для обновлённого списка устройств. Для этих возможностей обновите Server и Client. В существующие базы добавляются таблицы аватаров.

Делегированные правки ролевых и персональных правил требуют поддержки соответствующих подписанных действий v10 в Client и Server. Под действующим серверным deafen обновлённые Client и Server API 3 поддерживают переподключение с медиагрантом без ключа и без прав на звук.

Для делегирования ролей API 3 выдаёт данные в пределах конкретного действия через `GET /api/v3/roles/scoped` и проверяет черновик через `POST /api/v3/roles/scoped/preview`. Для назначения нужен профиль из списка участников доступного текстового канала или из каталога сервера при наличии права на него. Редактирование получает доступную часть порядка ролей. Предпросмотр привязан к текущей ревизии и включает суммарные последствия в видимых инициатору каналах. `POST /api/v3/roles/scoped/commit` принимает подпись устройства под точным изменением и возвращает компактную квитанцию с подписью сервера. Для полной проверки цепочки Client должен поддерживать подписанное действие `roles.scoped`. Действующий маршрут `roles.update` доступен владельцу и Administrator.

API 3 возвращает `PROTECTED_DEVICE_REVOKED` отозванному устройству активного профиля после проверки токена сессии или подписи при входе. Обновите Server и Client, чтобы устройство получало уведомление об отвязке, а сервер исчезал из его списка.
После явного разъединения профилей обновлённый Server возвращает `PROTECTED_PROFILE_UNLINKED` при подписанной попытке входа отсоединённого устройства. Обновлённый Client убирает сервер из его списка и предлагает присоединиться по новому приглашению.

Клиенты API 3 без актуального подтверждения политики передают `transition=1` в запросе на получение ограниченной задачи ротации. Обновлённый Server резервирует задачу только при наличии доказательства перехода и требуемых подтверждений. Обновите Client и Server вместе, чтобы избежать ожидания лишней аренды после изменений состава участников.

При наличии `protectedOwnerProfileAvatar` Client владельца повторно публикует существующий аватар профиля для активных устройств участников. Клиент получает зашифрованное изображение и пакет ключа своего устройства, когда владелец виден в запрошенном списке участников. Обновите Server и Client, затем подключитесь с устройства, которое может открыть текущий аватар владельца, чтобы опубликовать недостающие пакеты.
При наличии `protectedMemberProfileAvatars` участник с правом просматривать список участников сервера может зашифровать свой аватар для активных устройств участников через `shared=members`. Запрос `profileAvatars=all` возвращает пакеты только для видимых в списке профилей и только для устройства, которому они адресованы. Старые клиенты по-прежнему запрашивают только аватар владельца. Обновлённый клиент может повторно опубликовать существующий аватар, если может его расшифровать и сервер сообщает о недостающих пакетах.

# Обязательное сквозное шифрование / Mandatory E2EE

Документ описывает исходники API 2. Исторические опубликованные API 1 бинарники
не меняются. Форматы и точные контексты: [API-V2.md](API-V2.md).

## Что защищает каждый механизм

| Механизм | Назначение | Граница |
| --- | --- | --- |
| TLS и отпечаток приглашения | Защищают соединение с нужным сервером; pin проверяется до HTTP с доказательствами личности | Сервер является концом TLS и видит служебные запросы |
| Подписи профиля/устройства | Доказывают владение ключом устройства; одноразовый challenge и контекст сервера защищают от replay | Сервер отдельно проверяет актуальное членство, роль и бан |
| Приглашение | Разрешает вступить в течение TTL; admission token расходуется по правилам ссылки | Истечение не завершает членство уже вступивших |
| Членство и роли | Ограничивают API, историю, приглашения, каналы и новые голосовые grants | Не уничтожают ранее доставленные копии и ключи |
| E2EE | Скрывает содержание текста, вложений и аудио от Go API/медиасервера | Не скрывает IP, состав участников, размеры и время трафика |

Отсутствие TLS не означает шифрования. TLS и E2EE выполняют разные задачи:
первый защищает транспорт до сервера, второй — содержимое между устройствами.

## Первоначальная настройка

Selfhost автоматически назначает клиент создателя первым администратором.
Для чистого постоянного сервера CLI `initial-admin` или кнопка Manager выдаёт
одноразовую ссылку на 24 часа. Первый клиент создаёт случайный 256-битный root,
сохраняет его в защищённом хранилище ОС и только затем подтверждает членство.
Сервер сохраняет идентификатор ключа, а не root. После инициализации host-only
ссылки администратора недоступны; следующий администратор вступает обычно и
получает роль от действующего администратора. Отдельного генератора ключей нет.

## Приглашения и доставка секрета

Администратор или модератор создаёт одноразовую ссылку на 24 часа либо многоразовую
на час; лимит — по 100 активных ссылок каждого типа на сервер. Клиент приглашавшего
создаёт encrypted key package. Admission token и ключ открытия различны; ключ
открытия остаётся во fragment ссылки и не передаётся серверу.

Получателю не требуется онлайн-приглашающий. Он резервирует вступление на 120 секунд
(не дольше TTL), получает пакет, проверяет его контекст, расшифровывает и сохраняет
root в OS vault. Только после этого отправляет confirm. Повтор confirm восстанавливает
результат. Истёкшая неподтверждённая резервация не даёт доступа: этому устройству
понадобится новая ссылка. Отзыв/TTL удаляют пакет, не затрагивая уже вступивших.

Передавайте полную ссылку приватно: владеющий ею может воспользоваться приглашением.
Сервер, получивший и admission token, и ключ открытия извне, также сможет открыть
пакет; секретность ссылки является частью этой модели доверия.

## Ключи каналов

Из root посредством HKDF-SHA-256 выводятся ключи по server ID, channel ID и
назначению: голос, сообщения, вложения, профиль. Для текста/вложений используется
AES-256-GCM с новым случайным nonce и контекстом в AAD. Для аудио — штатный
LiveKit E2EE SDK с производным ключом голосового канала.

Все участники сервера знают один root и могут вывести эти ключи. Это разделяет
криптографические контексты, но не создаёт закрытых каналов. Если позже появятся
права каналов, одни ACL ограничат выдачу API; независимая криптографическая
изоляция потребует отдельно спроектированной доставки ключей.

## Устройства и ограничения

Каждая установка имеет собственную подписывающую личность. Связь подтверждается
только в контексте одного сервера через X25519 и подписанный обмен. Код живёт
10 минут; оба устройства должны быть онлайн. Ни root, ни закрытые ключи подписи
не появляются в renderer/API. В renderer выдаётся только текущий производный
голосовой ключ. Windows использует настоящий Electron safeStorage; сбой хранилища
останавливает вступление, без plaintext fallback.

Отвязка меняет полномочия и отображение авторства; root не меняется. Кик/бан/выход
не запускают ротацию. Уже известные ключи и скачанные сообщения нельзя отозвать.
Компрометация root позволяет расшифровать доступные зашифрованные данные; forward
secrecy и восстановление потерянного основного устройства сейчас отсутствуют.

API прекращает выдавать grants после отзыва членства и пытается удалить участника
из LiveKit. Принято ограничение: выданный media JWT может повторно использоваться
до истечения своего срока; модифицированный клиент не ограничивается поведением
официального UI. Абсолютное немедленное криптографическое отключение не обещается.

## English

API 2 requires E2EE. TLS authenticates and protects the transport; framed device
signatures prove identity; current membership/roles authorize API actions. A TTL
invitation permits admission and delivers an opaque encrypted root package. Clients
save the root in OS-protected storage before confirming membership. The host never
receives the root or invitation opening key through the protocol.

HKDF derives channel/purpose keys from a shared server root. These contexts prevent
cross-channel substitution but provide no cryptographic channel ACL. AES-GCM
protects text/attachments; LiveKit SDK E2EE protects voice. Leaving, unlinking,
kicks and bans do not rotate keys or erase prior copies. There is no forward
secrecy/recovery code. Issued media tokens retain their accepted reuse window.
Metadata remains visible. See [API-V2.md](API-V2.md) for the wire contract and
[MULTICHANNEL-PLAN.md](MULTICHANNEL-PLAN.md) for completed and pending verification.

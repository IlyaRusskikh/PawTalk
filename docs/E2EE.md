# Экспериментальное сквозное шифрование

Режим выключен по умолчанию. Используется штатный LiveKit SDK `encryption`, AES-GCM для сжатых аудиокадров и шифрование пользовательского data channel. Ключ — случайные 256 бит, отдельно от пароля входа. Он создаётся на клиентском компьютере и не передаётся Go API или LiveKit. Сигнализация, IP, список участников, длительность и объём трафика остаются видимыми серверу.

## Комната из приложения

В форме «Создать комнату» отметьте **«Сквозное шифрование E2EE»**. Клиент создаст ключ и включит его в приглашения. Участникам нужен обновлённый Voicecord. Приглашение содержит пароль и ключ — передавайте его только участникам по доверенному каналу.

При сохранении комнаты в закладки пароль и ключ сохраняются отдельно в защищённом хранилище Electron/Windows. При каждом запуске встроенного сервера создаются новый ключ и TLS-сертификат, поэтому гостям нужно свежее приглашение.

## VPS

На **своём доверенном клиентском компьютере**, не на VPS, создайте ключ одним
из способов. Все варианты создают совместимые ключи; каждый запуск выдаёт новый ключ.

> **Важно: сразу сохраните оба значения из генератора!**
> `Client key (SECRET): …` (в Node.js-версии — `Ключ для клиентов (секрет): …`)
> нужен для подключения участников, а `VOICECORD_E2EE_KEY_ID=…` — для `.env` сервера.
> Эта пара показывается только при данном запуске: генератор не сохраняет её в файл,
> а повторный запуск создаст **новый** ключ и отпечаток. До закрытия окна сохраните
> оба значения в менеджере паролей. Из отпечатка нельзя восстановить секретный ключ.
> Если ключ потерян, создайте новую пару, обновите `VOICECORD_E2EE_KEY_ID` на сервере,
> примените конфигурацию и передайте новый секретный ключ всем участникам.

### Из приложения

На главном экране Voicecord в блоке **«Настраиваете сервер?»** нажмите
**«Сгенерировать ключ шифрования»**. Адрес сервера и запущенный контейнер не нужны.
В модальном окне появятся секретный ключ E2EE, его SHA-256 хэш и готовые строки
`.env`: `VOICECORD_E2EE=true` и `VOICECORD_E2EE_KEY_ID=…`. Все значения можно скопировать.

Сохраните секретный ключ у себя и не передавайте незнакомым людям. Он нужен
участникам для подключения; на VPS перенесите только строки `.env` с хэшем.
Приложение не запоминает эту пару: сохраните её до закрытия окна. Каждое открытие
генератора создаёт новый ключ, поэтому не открывайте его заново для каждого участника.
При входе в настроенный сервер используйте сохранённый ключ, а не создавайте новый.

### Скрипт: Windows без Node.js

Скачайте [e2ee-key.cmd](../scripts/e2ee-key.cmd) и
[e2ee-key.ps1](../scripts/e2ee-key.ps1) в одну папку (на GitHub откройте файл и
нажмите **Download raw file**). Запустите `e2ee-key.cmd` двойным щелчком — окно
останется открытым, чтобы скопировать результат. Устанавливать Node.js или
зависимости проекта не нужно: используется встроенный Windows PowerShell.

Из CMD в папке исходников проекта:

```bat
scripts\e2ee-key.cmd
```

Для готового приглашения с **новым** ключом передайте ссылку в двойных кавычках:

```bat
scripts\e2ee-key.cmd "voicecord://IP:18443/ОТПЕЧАТОК_СЕРТИФИКАТА"
```

Напрямую через PowerShell:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\e2ee-key.ps1
```

`Client key (SECRET)` — секретный ключ для клиентов. На VPS копируйте только
строки `VOICECORD_E2EE=true` и `VOICECORD_E2EE_KEY_ID=…`. Генератор работает локально,
не обращается к сети и не сохраняет ключ в файл.

### Скрипт: любая ОС с Node.js

В папке исходников проекта:

```sh
node scripts/e2ee-key.mjs
```

Команда покажет секретный ключ для клиентов и публичный `VOICECORD_E2EE_KEY_ID` — SHA-256 от 32 байт ключа. На VPS передайте только идентификатор, ключ туда копировать не нужно.

### Настройка VPS

Добавьте в `.env` на VPS:

```dotenv
VOICECORD_PUBLIC_IP=ПУБЛИЧНЫЙ_IP
VOICECORD_E2EE=true
VOICECORD_E2EE_KEY_ID=ПУБЛИЧНЫЙ_SHA256_ОТПЕЧАТОК_КЛЮЧА
```

```sh
cd /opt/voicecord
docker compose -f compose.server.ghcr.yaml up -d
docker compose -f compose.server.ghcr.yaml exec server /voicecord serve info
```

Передайте приглашение из последней команды в локальную команду генерации, если ключ ещё не создавали:

```sh
node scripts/e2ee-key.mjs 'voicecord://IP:18443/ОТПЕЧАТОК_СЕРТИФИКАТА'
```

Она создаёт **новый** ключ и готовое приглашение с ним. Используйте именно выведенный с ним `VOICECORD_E2EE_KEY_ID` в `.env`. Если ключ уже создан, в клиенте можно открыть обычное приглашение VPS и ввести существующий ключ в форме подключения; после входа «Пригласить пользователя» включит его в ссылку. Пароль входа остаётся прежним.

Альтернативный флаг для прямого запуска образа: `voicecord-server:local --e2ee` (вместо `VOICECORD_E2EE=true`); идентификатор задаётся через `VOICECORD_E2EE_KEY_ID` либо аргумент `--e2ee-key-id=<sha256>`. Сетевые порты и volume — как в [SERVER.md](SERVER.md).

При `VOICECORD_E2EE=true` старые клиенты без поддержки E2EE получают HTTP 426. Если задан `VOICECORD_E2EE_KEY_ID`, API также отвергает неправильный ключ по его идентификатору (HTTP 403). Без этого идентификатора разные ключи обнаруживаются только при попытке расшифровки голоса, поэтому идентификатор рекомендуется задавать всегда.

## Что означает обязательное шифрование

Наш API требует заявление поддержки E2EE и идентификатор ключа. Клиент не публикует микрофон до включения шифрования, не переходит на незашифрованный режим при ошибке, проверяет `isEncrypted` до подписки на чужие дорожки и закрывает соединение при ошибке расшифровки или появлении незашифрованной дорожки. Приглашение с ключом требует подтверждения E2EE от API; ключ из ответа сервера не принимается.

SFU не способен криптографически доказать, что произвольный изменённый клиент честно шифрует своё содержимое. Клиент с действительным токеном может попытаться публиковать plaintext; защищённые клиенты отвергнут такую дорожку до воспроизведения. Он может мешать разговору, вызывая защитное отключение. Это ограничение важно отличать от гарантии конфиденциальности исходящего голоса исправного клиента.

Любой обладатель общего ключа может расшифровывать разговор. Автоматической смены ключа при уходе участника, защиты прежних записей при последующей утечке общего ключа (forward secrecy) и персональной криптографической проверки участников в этой версии нет. Для отзыва доступа создайте новый ключ, обновите идентификатор на VPS, перезапустите комнату и раздайте новое приглашение оставшимся участникам.

## Текстовый чат

Встроенный сервер держит историю E2EE-комнаты в памяти. Участники могут выйти и вернуться к переписке, пока сервер работает. При остановке встроенного сервера вся история очищается. Отдельный сервер из Docker-образа хранит историю в `/data/chat.sqlite`, когда включён `VOICECORD_E2EE` и задан `VOICECORD_E2EE_KEY_ID`.

Оба режима используют одно API. Во встроенной комнате хранится до 500 сообщений. В версии 0.5.0 отдельный сервер использует `VOICECORD_CHAT_MAX_MB` (128 МиБ по умолчанию, `0` — без лимита) вместо ограничения на возраст и количество: учитываются сообщения, изображения, профили и индексы, старейшая история удаляется с освобождением места. Опубликованная 0.4.1 сохраняет прежние ограничения. Voicecord выводит отдельный ключ чата через HKDF и шифрует текст на клиенте через AES-GCM. Сервер получает зашифрованный текст и видит никнейм, время и порядковый номер сообщения. Сервер проверяет формат пакета, а подлинность шифротекста проверяют клиенты при расшифровке.

Участник с текущим ключом может прочитать доступные сообщения текущей ленты, в том числе отправленные до его входа. Для встроенной комнаты отметка прочитанного остаётся в памяти клиента, а для отдельного сервера хранится на устройстве. Перезапуск отдельного сервера с тем же отпечатком сохраняет ленту и её нумерацию. При смене отпечатка сервер создаёт новую ленту, а записи прежней остаются в базе до обычной очистки.

Сообщения привязаны к ID профиля. Сервер видит ID и никнейм, а аватар хранится зашифрованным отдельным ключом, выведенным из ключа комнаты. Профиль остаётся доступен, пока в ленте есть сообщения автора, даже если он вышел. Встроенный сервер очищает профили вместе с историей при остановке. Дорелизная база чата предыдущего формата начинает новую ленту при первом запуске с этой схемой.

## Проверки и сравнение производительности

```sh
node scripts/e2ee-benchmark.mjs --security-only
node scripts/e2ee-benchmark.mjs
```

Нужны установленные npm-зависимости, Go для сборки встроенного сервера и работающий Linux Docker Engine. Скрипт автоматически собирает API, контейнер, запускает отдельный Vite на 5194 и настоящий Electron. Свободные тестовые порты: 32443–32445 и 33443–33446. Используются отдельный Docker volume и временный WAV; производственная конфигурация не меняется. Отчёт: `release/qa/e2ee-benchmark.json`.

Проверяются VPS-контейнер и встроенная комната: отказ старому клиенту, неверному ключу, зашифрованный двусторонний звук, повторный вход, невозможность расшифровать звук одним токеном без правильного ключа и отказ от plaintext-дорожки изменённого клиента.

Для измерений запускаются два клиента на одном компьютере, передающие одинаковую локально синтезированную речь Windows SAPI. Личные записи не используются. На других ОС можно указать `--audio-file=/путь/к/речи.wav` (PCM16, mono, 48 кГц); без речевого WAV выполняется только серия без шумоподавления с синтетическим тональным сигналом, поскольку RNNoise его подавляет. Сервер — Linux LiveKit в Docker Desktop. В каждой серии порядок **без E2EE → с E2EE → с E2EE → без E2EE**. Отдельные серии — с RNNoise и с выключенным шумоподавлением. Каждый прогон прогревается шесть секунд, плюс 1,5 секунды для стабилизации часов измерителя, затем измеряется 24 секунды. Длительность можно увеличить аргументом `--seconds=60`; `--quick` оставляет только серию без шумоподавления.

CPU рассчитывается из накопленного процессорного времени, включая потоки worker. **100% = одно логическое ядро**. В отчёте отдельно указаны процессы двух клиентов и весь Electron с общими служебными процессами. Показания диспетчера задач, нормированные на все ядра, будут другими.

Тестовые окна используют настоящий `VoiceSession`, но не отрисовывают весь интерфейс приложения; аппаратное ускорение Electron выключено. Поэтому абсолютная загрузка готового приложения может отличаться. Эти условия одинаковы для E2EE и контрольных прогонов.

Задержка измеряется корреляцией огибающей речи от необработанного захвата микрофона до декодированного сигнала на узле громкости другого клиента в неперекрывающихся двухсекундных окнах. Диапазон поиска 0–501 мс, минимальная корреляция — 0,5. Часы AudioContext сопоставляются через `getOutputTimestamp`; проверяется их дрейф. Разрешение измерения около 2,67 мс (128 сэмплов при 48 кГц). Это программный аудиотракт, **не физическая задержка «рот — динамик»**: реальные устройства, акустика и интернет не включены. Небольшие различия в пределах дискретности и джиттера не доказывают ускорение или замедление. Нагрузки игры и больших групп в этом тесте нет.

SDK LiveKit отключает аудио RED (дублирование для восстановления потерь) при E2EE. Поэтому сравниваются реально используемые режимы приложения целиком, а не только стоимость AES. Устойчивость зашифрованного режима при потерях пакетов в этом эксперименте не измеряется.

Основание реализации: [официальное руководство LiveKit](https://docs.livekit.io/transport/encryption/start/). Экспериментальные результаты и ограничения замера следует учитывать до включения по умолчанию.

Результаты выполненной серии на Intel Core i3-12100F: [E2EE-BENCHMARK.md](E2EE-BENCHMARK.md). Исходные измерения сохраняются локально в `release/qa/e2ee-benchmark.json`, сводная таблица генерируется командой `node scripts/summarize-e2ee.mjs`.

После этой серии аудиотракт оптимизирован: сравнение общего и отдельных AudioContext с включёнными RNNoise и E2EE находится в [LATENCY.md](LATENCY.md). Проверки `--security-only` сохраняются отдельно в `release/qa/e2ee-security.json` и не заменяют результаты измерений.

# Проект ключей каналов и условия включения

Статус: проект. Синтетические проверки покрывают граф архивных ключей и адресацию правок на ключах в памяти. API 2 не содержит пакетов ключей каналов и подписанной цепочки политик.

## Полномочия и контрольные точки

Корень доверия должен связывать ID сервера и начальную политику с открытой идентичностью первого владельца. При вступлении проверяется подпись уполномоченного создателя приглашения относительно этого корня. Подписываются срок, лимит и отдельный проверочный ключ приглашения. Ссылка содержит соответствующий секрет подписи вступления, который не передаётся серверу. Вступающий подписывает этим секретом ID сервера, приглашения и вступления, профиль и точный сертификат устройства, а владение ключами устройства доказывает отдельно. Проверяющий сверяет срок, счётчик и уникальность с предыдущим состоянием политики. Воспользоваться приглашением в заданных пределах может любой держатель ссылки. Подтверждённое использование, актуальная политика и готовность recovery определяют публичных получателей ключей. До передачи учётных данных проверяется TLS-идентичность сервера.

Использовать версионированные домены и существующий формат PawTalk с префиксами длин. Подписывать ID сервера, хеш предыдущей политики, номер версии, ID логической операции, профиль и устройство автора, основание и нормализованную мутацию. Проверять полномочия автора по предыдущей подписанной политике и предложенному результату. Сертификат устройства связывает эффективный профиль, ключи подписи и шифрования и версию авторизации. Подпись ротации связывает канал, хеш политики, ожидаемое предыдущее поколение, задачу, поколение, устройства или резервных получателей, назначения и хеши пакетов. Вычислять состав получателей по проверенной политике. Lease даёт право попытаться выполнить задачу. Для принятия результата требуются проверка основания и атомарное сравнение с исходной версией задачи.

Перед использованием сохранять проверенную контрольную точку политики и головы каналов в защищённом хранилище Electron. Известная старая точка и другой хеш при том же номере блокируют отправку. При продвижении нужна проверяемая связь с сохранённой головой. Без независимого свидетеля более новой версии клиент не отличит неизвестное ему обновление от его сокрытия сервером. Это касается восстановления и статуса офлайн даже при корректных подписях. Для G4 нужны протокольные и сквозные проверки доказательств, подстановки и конкурирующих версий.

Закреплённое устройство владельца может после проверки полной цепочки подписать отдельное подтверждение корня `pawtalk-policy-scope-attestation-v1`. Подпись связывает сервер, исходную контрольную точку, ревизию и её отпечатки с версией и значением поканального корня. API 3 выдаёт только эти утверждения, подпись и открытый ключ устройства. Обычный участник проверяет ключ по закреплённому ID, сохраняет контрольную точку и сверяет своё доказательство допуска, включая первую позицию и право полной истории. Клиент отклоняет известный откат и конкурирующую запись той же ревизии.

При запросе узких доказательств API 3 прикладывает свидетельство устройства подписанта к выдаваемому поколению ключа и свидетельство автора к доступному live-сообщению. Оно строится из подписанной политики поколения и отдельного пути устройства в дереве видимого канала. Маршрут доступного объекта определяет подписанта. Для устройства с проверяемым допуском к текущему непрерывному интервалу Client открывает адресные live-пакеты, читает и отправляет сообщения без загрузки полного снимка. Читатель с полной историей также проходит по подписанным архивным связям с узкими доказательствами подписантов. После обхода Client повторно проверяет текущий допуск к полной истории. Для перенесённого текста Client сверяет проверенное исходное архивное поколение со связью переноса и проверяет подписи владельца. Автономная проверка полномочий делегированного автора политики остаётся открытой.

Лист канала v6 также фиксирует отдельные списки получателей живой и архивной ротации. Каждый список использует отдельную соль для канала, назначения и ревизии политики. Исполнитель с действующим назначением получает соль только для своего назначения. До шифрования он пересчитывает отпечаток полного списка и проверяет допуск своего устройства. Для архивной ротации он также проверяет исторических подписантов исходных пакетов, подпись предыдущего архивного поколения и непрерывность живого диапазона. Фоновый исполнитель может подхватить доступную задачу по уже опубликованному подтверждению владельца.

При восстановлении соединения закреплённое устройство владельца получает до четырёх номеров неподтверждённых ревизий. Оно проверяет их за один проход от исходной подписи до локально проверенной контрольной точки, затем публикует подтверждение текущей ревизии и заполняет пропуски. TLS-тест покрывает восстановление двух пропущенных подтверждений, отказ при подмене исторического снимка и запрет выдачи списка обычному участнику. Делегированному изменению по-прежнему нужно отдельное доказательство полномочий и влияния на получателей без раскрытия скрытых каналов.

При изменении с закреплённого устройства владельца Client отправляет подпись политики и подтверждение поканального корня одним запросом. Сервер фиксирует доказательства вместе с новой политикой, задачами ротации и записью аудита. Квитанция точного повтора возвращает уже записанное доказательство. TLS-тест отклоняет неверную подпись подтверждения без изменения ревизии, затем имитирует потерю ответа. Обычный участник получает подтверждение сразу после записи, а повтор возвращает тот же отпечаток без повторного применения.

При подготовке миграции Client аналогично подписывает подтверждение первого корня. `migration-stage-policy` сохраняет его вместе с исходной политикой. Интеграционный тест отклоняет повреждённое подтверждение до сохранения исходной политики, повторяет подготовку без изменения отпечатка и проверяет, что после переключения обычный участник получает подтверждение первой ревизии.

В проекции v8 голосовой лист закрепляет дерево допущенных устройств с раздельными солями. Запись связывает эффективный профиль, публичный ключ согласования и ключ подписи. В дерево входят действующие устройства с Connect без deafen. Mute, Speak и тайм-аут по-прежнему проверяются в рабочих голосовых операциях. Server загружает состав конкретного периода и его доказательства в одной транзакции. Основной процесс проверяет текущий подтверждённый корень, канал, отпечаток состава, каждое устройство и подпись автора пакета. Допуск доказуем по подписанной политике, сведения о присутствии конкретной сессии поступают от Server. Текстовые листья сохраняют формат v7. Существующие сохранённые основания v3–v7 остаются проверяемыми.

Лист политики v7 фиксирует тип и категорию канала и дерево устройств с действующим правом `channel.edit`. В дерево входят подписывающие устройства независимо от регистрации ключа шифрования. Сервер раскрывает только запись запрашивающего устройства для разрешённого канала. Для предпросмотра делегированной перестановки Client сверяет исходный и опорный каналы по одному подтверждённому корню, проверяет допустимую группу и сравнивает возвращённую операцию с запросом. TLS-тест покрывает предпросмотр для пары «текстовый и голосовой в одной категории», отказ после отзыва права и подмену категории или опорного канала. Подписанная запись перестановки проверяется при сохранении. Автономная проверка её результата другими клиентами остаётся открытой.

Лист v10 связывает тип и категорию канала, корень редакторов порядка, отпечаток настроек v9 и корень доказательства ACL. Корень ACL связывает два отпечатка. Первый включает признак синхронизации, SHA-256 канонического JSON применимых ролевых правил и соль HMAC канала. Второй закрепляет дерево устройств с действующим `channel.access.edit`, с раздельными HMAC для соли и порядка. Для открытия Server проверяет действующее право в транзакции и выдаёт только применимые ролевые правила и доказательство устройства запрашивающего. Персональные правила остаются в полной политике. Client сверяет корень предыдущей подписанной аттестации и доказательство.

Подпись делегированного изменения связывает сервер, границу миграции, профиль и устройство, операцию, точную предыдущую ревизию и отпечатки старых и новых ролевых правил. Server дополняет изменение действующими персональными правилами внутри транзакции. При воспроизведении полной политики Client заново проверяет подпись, полномочия, допустимость перехода и границы допуска. Узкие получатели используют новую аттестацию для проверки права на ключ. Проверка всех эффектов перехода в узкой области без новой аттестации остаётся открытой.

Для персонального изменения устройство подписывает идентификатор целевого профиля, одно разрешение и состояние `allow`, `deny` или `inherit` вместе с каналом и точным предшественником. Право редактора подтверждается v10. Отдельный запрос в той же области возвращает правила только выбранного профиля. Условия видимости, ранга и эффекта проверяются при применении и при полном воспроизведении. Атомарное изменение локализует эффективный ACL по типу канала и заменяет только подписанное разрешение.

Проекция v11 добавляет лист `@pawtalk-profile-ranks` к дереву политики. Он закрепляет сжатое двоичное дерево рангов активных эффективных профилей. Соль HMAC ревизии и идентификатора отделяет позицию и отпечаток записи от открытого ID. Запись связывает ID, ранг и соль. Критическое действие открывает доказательства для инициатора и выбранной цели. Client сверяет корень с аттестацией, пути к двум записям и строгую иерархию до подписи запроса. Остальные профили остаются закрыты. Это доказательство относится к предыдущей политике. Проекция v12 связывает с той же записью ранга факт обхода ACL канала. Владение и базовое право `server.administrator` проверяются независимо от ранга. Последствия нового допуска по-прежнему проверяются отдельно.

API 3 сохраняет перестановку отдельной подписанной операцией. Устройство подписывает исходный и опорный каналы, направление, ID операции, голову политики и отпечаток доступной ему для изменения последовательности. Вторая версия вычисляет отпечаток через HMAC из закрытого seed политики, с привязкой к автору и исходному каналу. Так получатель доказательства не может проверять догадки о составе скрытых каналов по открытому хешу. Старые квитанции сохраняются для повторов операции. Server проверяет подпись, оба разрешения и совпадение последовательности в транзакции. Порядок, квитанция и запись аудита сохраняются вместе. Фильтр ленты каналов использует этот порядок, сохраняя позиции скрытых и недоступных для правки каналов. Перестановка работает по текущей подписанной политике и не требует смены её ревизии. Делегированный участник запускает предпросмотр и применяет перестановку в обычном окне. Оно предлагает только опорные каналы с правом правки из допустимой группы и закрывает диалог при отзыве доступа. Журнал аудита проверяет конкретную перестановку по отпечатку её подписи. Client сверяет подпись автора и оба доказательства `channel.edit` по исторической ревизии. Доказательство выдаётся при текущей видимости обоих каналов и сохранённой исторической группе. Полная проверка опубликованного порядка остаётся открытой. Например, если между двумя видимыми каналами меняется порядок из-за перестановки относительно скрытого канала, клиенту нужен способ проверить результат, сохранив скрытую опору.

Два делегированных изменения могут иметь действительные подписи для одной предыдущей политики. При принятии живого поколения без новой аттестации подпись поколения должна связывать точный переход канала, задачу, предыдущее поколение и отпечаток пакетов. Иначе доказательство одного корректного изменения можно приложить к поколению, выпущенному по другому. Проверенный переход служит основанием для живого поколения в этом канале. Глобальная политика проверяется по своей контрольной точке.

Живые сообщения такого поколения содержат поканальное доказательство для устройства конкретного автора по предыдущей политике. Читатель проверяет `message.send`, сохранение допуска автора и подпись его подтверждённым ключом. Подтверждённый переход служит основанием для статуса и отправки оставшегося участника, пока другая политика не потребует отдельного доказательства. Старые адресные live-пакеты сохраняют проверенную границу допуска и должны быть связаны с закреплённым поколением цепочкой подписанных записей.

Проекция v15 добавляет второе позиционное доказательство для получателей правок с ограниченной историей. Устройства одного эффективного профиля имеют общую границу непрерывного допуска. Лист профиля связывает всю группу с независимыми внутренней и внешней солями. Доказательство позиции закрепляет точный состав допущенных групп. В основании правки открываются только группы, которым доступна позиция оригинала. Предыдущий состав можно восстановить по закрытому листу исключённой группы и открытиям оставшихся. Внутренняя соль и устройства исключённого профиля остаются закрытыми. При подтверждённом одиночном персональном запрете оставшийся автор может зашифровать поканальную правку по этому доказательству до новой аттестации. Публичный ключ обёртки принадлежит проверенному архивному поколению того же перехода. Читатель проверяет автора оригинала и подписанта архива по историческому доказательству и отдельно подтверждает свой текущий допуск.

## Граф секретов канала

Прототип выборочного раскрытия строит из одной политики отдельное представление получателей для каждого текстового канала. В представление входят публичные ключи для пакетов, проверочные ключи устройств и допуск к архивному ключу. Для вычисления допуска используются существующие проверки View и Full History. Границы допуска других читателей и правила ACL в пакет доказательства не входят.

Для скрытия общего числа каналов дерево всегда содержит 1024 позиции. Позиции настоящих и заполняющих листьев определяются независимыми HMAC от закрытого случайного seed. Лист связывает хеш ID канала, отдельную соль и хеш представления. Получатель получает только соль своего листа, позицию и десять соседних хешей. Go формирует путь. Client с полной политикой пересчитывает корень и проверяет путь. Дифференциальный тест меняет канал, ключи допуска, соль и позицию.

Корень связан с сервером, автором и ревизией в домене подписи `pawtalk-protected-policy-v2`. При новой миграции первая соль дерева создаётся в транзакции регистрации ключа устройства владельца. Повторная подготовка использует сохранённую соль. При правке политики сервер выдаёт новую соль для полной предварительной проверки. Client владельца сначала воспроизводит переход и пересчитывает корень, затем подписывает. Сервер пересчитывает корень при commit и при проверке цепочки на старте. Ранее подписанная ревизия без корня остаётся читаемой. После появления корня цепочка не может снова перейти на формат без него.

Доказательство включения само по себе не устанавливает полномочия автора изменения. Самостоятельная проверка проекций зависит от проверки переходов по предыдущему состоянию, в том числе для делегированных авторов. Соль дерева остаётся в полном пакете проверки владельца.

В `pawtalk-protected-policy-v3` лист канала содержит корень отдельного дерева получателей. Запись привязывает эффективный профиль, устройство, ключи подписи и шифрования, право на архив и первую позицию непрерывного допуска. Соль и место записи вычисляются раздельными HMAC по каналу и получателю. API возвращает запись запрашивающего устройства, её соль, путь и число получателей видимого канала. Остальные записи и seed ревизии остаются закрыты. Client с уже проверенным корнем сверяет эту запись при открытии адресного пакета. Проекция v13 добавляет отсортированный отпечаток групп живых получателей по эффективным профилям. Для листа профиля и отпечатка его устройств и recovery используются независимые соли HMAC. Проверяющий может восстановить предыдущий подписанный корень из оставшихся групп и одного закрытого листа удалённой группы. Для этого достаточно внешней соли и отпечатка группы. Внутренняя соль и записи удалённых устройств остаются закрыты. Обычная поканальная живая ротация проверяет открытие всех текущих групп. При одиночном делегированном запрете `channel.view` Client может выпустить живое поколение и открыть адресный ключ по предыдущей аттестации и подписанному переходу, пока новая аттестация недоступна. Адресату видны только доказательства его прежнего допуска и допуска издателя. Другие переходы живых поколений используют аттестацию. Проекция v14 связывает группы архивных получателей с независимыми солями и доменами. Поканальная архивная задача открывает только точный состав архивных получателей. При одиночном запрете для профиля с полной историей отдельное доказательство по предыдущему архивному составу показывает точное исключение без раскрытия прежних устройств. Подпись архивного поколения включает отдельный архивный отпечаток перехода и ключ обёртки. Без новой аттестации исполнитель проверяет предыдущий архив и пачку источников, которая доходит до подписанного живого поколения того же запрета. Читатель открывает адресное архивное поколение по прежнему допуску к полной истории своего устройства и издателя, проверяет обратные ссылки и повторно сверяет текущее поколение перед выдачей открытого текста. Для неполной пачки исполнитель проверяет последний живой источник по закреплённой цепочке. Последующие архивные пачки того же перехода содержат поканальное доказательство издателей промежуточных поколений. Если у исключённого профиля была только живая история, Client сверяет неизменный архивный состав с предыдущим архивным корнем. Ранее адресованный recovery-пакет можно использовать для старого источника при неизменной recovery-идентичности и сохраняющемся допуске к полной истории до и после запрета. Исполнитель сверяет допуск recovery по предыдущей аттестации и подпись старого источника по аттестованной политике источника. Для нового живого источника используется адресный пакет действующего устройства. Старые ревизии v2 остаются проверяемыми, а откат к уже пройденной версии формата отклоняется. Выдача старого live-пакета в пределах непрерывного допуска содержит доказательство устройства для ревизии поколения. Client сверяет его с проверенным историческим корнем, затем повторно проверяет текущий допуск. Если обе ревизии совпадают, достаточно одного доказательства. Новая миграция закрепляет v9 при регистрации устройства владельца. Ранее подготовленная миграция сохраняет исходный формат и отпечаток. Обновлённый Client предлагает v17 при подписанном изменении рабочей политики.

Проекция v16 добавляет корень дерева Меркла с учётом числа листьев для точных потерь видимости при одиночном запрете channel.view по именованной роли. Выбранный лист фиксирует роль, канонические хеши правил до и после изменения и список эффективных профилей, потерявших допуск. Разрешение по другой именованной роли, персональное разрешение или полномочия администратора сохраняют видимость. Исполнитель поканальной живой ротации проверяет предыдущую аттестацию, подпись редактора и доказательство эффекта. Он восстанавливает проверенный прежний корень по текущим группам и закрытым листьям исключённых групп. У исключённого профиля может отсутствовать лист, если у него не было допущенного устройства или ключа восстановления. Подпись нового живого поколения фиксирует хеш перехода для запрета по роли. До новой аттестации поканальный читатель проверяет эффект, собственный предшествующий допуск и допуск подписанта поколения. Для отправителей сообщений используется тот же предшественник. Читатель отдельно проверяет границу непрерывного допуска. Исходные правила ACL и сведения об устройствах исключённых профилей остаются закрытыми. Архивная аренда использует тот же эффект запрета и независимо засоленные архивные группы. Исполнитель сверяет границу пакета источников с проверенной живой цепочкой того же перехода. Подпись архивного поколения закрепляет отдельный хеш перехода и публичный ключ обёртки. Поканальный читатель проверяет адресный пакет, текущую голову и связанные архивные поколения перед выдачей истории. Для источника, адресованного ключу восстановления, проверяются точный допуск полной истории и неизменная идентичность восстановления. При поканальной правке после запрета по роли автор восстанавливает цепочку доказательства на позиции оригинала по оставшимся группам ограниченной истории и закрытым листьям исключённых групп, допущенных к оригиналу. Автор проверяет, что подписанный архивный ключ обёртки покрывает живую голову того же перехода. Для сохранённой правки используются автор и подписант обёртки из неизменяемой архивной политики, а читатель независимо проверяет свой текущий допуск.

TLS API 3 выдаёт путь к текущему листу видимого текстового канала. Ответ содержит ID запрошенного канала, ревизию и хеш политики, отдельную соль листа и соседние хеши. Список получателей, ACL и координаты других каналов остаются в полном пакете. Сервер сохраняет только дерево текущей ревизии в кеше, а видимость заново проверяет в транзакции выдачи. Тот же путь входит в ответ с пакетом ключа для устройства. Client с проверенной полной цепочкой вычисляет ожидаемый лист и отказывается открывать пакет при несовпадении или отсутствии доказательства для ревизии с поканальным корнем. Для Client, который пока не имеет полной цепочки, путь ещё не даёт самостоятельного основания доверять корню.

При запуске Server воспроизводит полную цепочку на тех же правилах авторизации, что при commit. Проверка требует права на конкретный ресурс в предыдущем состоянии и совпадения всего результата и поканального корня. Снимок исключает текущие счётчики сообщений. Новый допуск использует позицию из подписанного снимка, непрерывный сохраняет исходную. За один переход все вновь допущенные к существующему каналу получают одну позицию, которая не может предшествовать уже подтверждённой для этого канала. Client хранит известную нижнюю границу в локальном контрольном снимке. Эта проверка не восстанавливает фактический счётчик из отсутствующих записей. Проверка полной цепочки является основанием для проектирования выборочного формата. Обычный участник пока не получает доказательство полномочий делегированного автора.

Адресный пакет использует базовый режим HPKE с X25519, HKDF-SHA256 и AES-128-GCM по [RFC 9180](https://www.rfc-editor.org/rfc/rfc9180.html). Один пакет содержит 32 байта инкапсуляции и 48 байт шифротекста с тегом. Домен связывает сервер, канал, основание политики, поколение, задачу и lease, получателя, его публичный ключ и назначение. В запись поколения с подписью Ed25519 входит корень отсортированного дерева пакетов. Клиент открывает только пакет с действительным доказательством включения. Доказательство показывает размер дерева и положение пакета, скрывая личности остальных получателей. Внутренний серверный адаптер выдаёт собственный пакет текущего поколения с проверкой актуального доступа. Проверка доверия к подписанту и основанию передаётся из проверенной цепочки.

В каждом поколении текстового канала создавать независимые живой и архивный секреты. Голова полного архива открывает живой ключ поколения и обратную ссылку на предыдущий архивный секрет. Устройству с полной историей достаточно выдать последнюю голову. Устройство с ограниченной историей получает только положенные живые ключи текущего непрерывного допуска. От живых ключей нет пути назад в архив. На новой границе ограниченного допуска нужна ротация до выдачи новому читателю живого ключа. При снятии полной истории сохраняется исходная граница непрерывного допуска, а секреты с сократившимся составом получателей ротируются.

У живого текста, файлов, обёрток правок и архивных звеньев отдельные контексты. Правка использует новый ключ содержимого. Упаковать его отдельно для текущих проверенных ограниченных читателей оригинала и под актуальной архивной головой для читателей полной истории. Будущий читатель полной истории сможет открыть эту обёртку по архивной цепочке. Контекст связывает ID сообщения, исходную позицию, номер редакции, её поколение, автора и устройство. Автор подписывает контекст и обязательства по шифротекстам каждой редакции. Производные объекты и метаданные ссылок следуют доступу к оригиналу в HTTP и подписках.

Архивное поколение формата `pawtalk-protected-epoch-v2` подписывает открытый X25519-ключ для обёрток редакций. Закрытый ключ получается из секрета архивного поколения через HKDF-SHA256 в отдельном контексте сервера, канала, поколения и идентификатора секрета. Автор с ограниченной историей сможет сформировать HPKE-обёртку по проверенному открытому ключу без получения архивного секрета. При открытии адресного пакета Client сверяет этот открытый ключ с производным от полученного секрета. Записи v1 остаются проверяемыми. При открытии постоянного Server старая архивная голова ставится в очередь обычной ротации без изменения её подписи или звеньев. Server и контрольная точка Client отвергают возврат к v1 после принятия v2.

Прототип редакции генерирует случайный 32-байтовый ключ для текста, один HPKE-пакет для архивной головы и отдельный HPKE-пакет для каждого ограниченного получателя из проверенного списка. Подпись Ed25519 привязывает область, исходную позицию и отпечаток оригинала, номер и предыдущий отпечаток редакции, операцию, автора и устройство, политику, архивную голову, шифротекст, архивную обёртку и корень адресных пакетов. Тест проверяет отказ при подмене этих полей, открытие через архивную цепочку и изоляцию от старого архивного секрета и чужих ключей устройств.

API 3 готовит и принимает правку только для автора с доступом к оригиналу и правом отправлять. Непринятая архивная ротация блокирует подготовку и публикацию. Транзакция повторно сверяет политику, архивную голову, предыдущую редакцию, точный набор ограниченных получателей и подпись, сохраняет редакцию с пакетами, квитанцией и записью аудита. Получатель с ограниченной историей может получить только свой адресный пакет с доказательством включения. Читатель с полной историей открывает редакцию через архив. Маршруты проверяют право читать оригинал по его исходной позиции при каждой выдаче. Удаление оригинала исключает редакции из активной выдачи.

Main-процесс проверяет подпись и отпечаток оригинала, полномочия автора на ревизии публикации и точный состав получателей по локально проверенной политике. При отправке он сверяет состав архивного поколения с текущим составом архивных читателей перед шифрованием. Новые редакции отображаются на исходной позиции и сохраняют время отправки. Открытая лента получает поканальные изменения по непрозрачному курсору, повторно проверяет доступ и заменяет загруженные сообщения на месте. Повтор запроса из открытого окна использует сохранённый зашифрованный пакет. Публикация с неподтверждённым составом останавливается. Поканальное доказательство v4 связывает право автора на отправку и отпечаток состава архивных читателей с подписанным корнем. Читатель проверяет совпадение архивного состава на ревизиях правки и архивного поколения. TLS-тест открывает адресный пакет для ограниченной истории и архивную обёртку для полной истории, отвергает подмену права автора и подтверждает отсутствие запросов полного снимка. Политика v5 также фиксирует точный набор ограниченных получателей на каждой исходной позиции. Доказательство для публикации раскрывает ключи и соль только запрошенного набора. Для других позиций оно передаёт соседние отпечатки. Автор проверяет полный список и архивный адрес до шифрования, а Server повторно сверяет основание при записи. Старые версии политики и переназначение автора перенесённого оригинала пока могут требовать полной цепочки.

Исполнитель с ограниченной историей может подготовить живой материал без архивного секрета. Для связывания головы нужен оставшийся проверенный хранитель прежней головы или отдельно доказанная схема связи. При отсутствии подходящего хранителя архивная работа остаётся в очереди. Для далёкой истории нужны ограниченные порции и проверяемые контрольные точки. Хранение звена определяется достижимостью оставшегося содержимого, отдельно от срока записи в аудите.

## Отзыв и повторы

При применении политики сохраняется первый дедлайн для поколения с отозванным получателем. Из старых ключей допустим только непосредственно предыдущий, и только до его исходного дедлайна. Текущее членство и доступ проверяются отдельно при записи и доставке. Официальный клиент сразу предпочитает полученный новый ключ. Предыдущий живой ключ по-прежнему открывает шифротексты, записанные под ним в grace. Правка старого объекта ждёт проверенного состава получателей и допустимой архивной головы. Если пакетное изменение одновременно отзывает прежних читателей и допускает новых ограниченных, прежний живой ключ новичкам не выдаётся. Для доставляемых им сообщений, принятых в переходе, нужны отдельные разрешённые пакеты или последующая перепаковка. До включения grace для смешанных операций нужен сквозной тест этого случая.

Использовать стабильный ID логической операции и отдельный ID криптографической попытки для каждого нового шифротекста. Сообщение и логический receipt фиксируются атомарно. При неопределённом ответе запрашивается receipt; повторная допустимая попытка возвращает уже зафиксированный результат. Логический ID связывает неизменяемые профиль, канал, вид операции и объект. Запрос receipt требует авторизации и не раскрывает закрытые метаданные. G3 требует гонок между принятыми, потерянными, устаревшими и перешифрованными попытками.

## Восстановление, миграция и голос

Из случайного локального recovery-секрета с разделением доменов выводится независимый материал подписи и получения ключей. Регистрируется только открытая резервная идентичность; для авторизации недостаточно открыть пакет. Recovery подписывает актуальный вызов, идентичность политики, действие и ключи нового устройства. Проверить по актуальной резервной идентичности и членству, отозвать прежние устройства и сессии в соответствующем сценарии и атомарно зафиксировать задачи ротации. G5 требует проверок бана, понижения, replay и старых пакетов.

При регистрации API 3 выводит открытые ключи из того же формата кода, что и миграция. Вызов действует 60 секунд и привязан к серверу, переключению, эффективному профилю, устройству и голове политики. Client подписывает намерение ключом резервной личности и ключом действующего устройства. Server проверяет владение отдельным X25519-ключом через HMAC от ECDH. Доказательство политики хранит публичные подтверждения, а обычный участник получает краткую квитанцию. При замене новые поколения получают новый резервный адресат, а прежние ключи помечаются отозванными. Готовность требует отдельного подтверждения открытия актуальных пакетов и не следует из регистрации.

Новый резервный пакет live или archive содержит внутри HPKE секрет поколения и отдельный случайный 32-байтовый seed подписи открытия. Соответствующий открытый ключ вместе с шифротекстом входит в лист дерева подписанного поколения. Пакет занимает 144 байта. Пакеты устройств и прежние 80-байтовые записи совместимы побайтно. Server ставит задачи для допустимых устаревших runtime-пакетов при запуске, сохраняя подписанные поколения и аренды.

API 3 выдаёт список пакетов текущей резервной идентичности в доступных каналах, а Client открывает каждый пакет отдельно. Для archive нужно право полной истории. Для live с ограниченной историей сверяется непрерывный допуск по текущей и исторической политикам. Client сверяет подпись поколения, корень пакетов, идентификатор открытого секрета и ключ подтверждения. Ключи открытия и резервной идентичности подписывают вызов для каждого пакета. Резервная идентичность и действующее устройство подписывают отпечаток полного перечня. Server проверяет обе подписи каждого пакета, его включение в подписанное поколение, текущий допуск и точный состав поколений. Готовность фиксируется в той же транзакции, поэтому смена политики или поколения отклоняет весь запрос.

При потере всех устройств резервная идентичность и новый ключ подписи подтверждают одну замену, а владение ключом получения нового устройства проверяется отдельным HMAC от ECDH. Вызов связан с текущим основанием политики и переключением сервера. Подписанное изменение сохраняет профиль, роли и ограничения, отзывает старые устройства и сессии и запускает ротации. В архивной задаче резервный пакет открывается только для точной цели аренды при праве полной истории. При ограниченной истории старый live-пакет выдаётся только при совпадении начала текущего и исторического непрерывного допуска.

После восстановления владельца поканальные аттестации v2 заверяет новое устройство. Исходный ключ владельца остаётся закреплённым в genesis. От него строится отдельная цепочка полномочий: текущий подписант авторизует резервный ключ, а действующая резервная идентичность и новое устройство подписывают смену подписанта. Каждый переход привязан к действию и ревизии политики. Получатель проверяет только компактные доказательства и хранит последнюю принятую вершину для отказа при известном откате. Исторические аттестации v1 сохраняют свой формат. Новый подписант может подтвердить проверенную историческую ревизию, указывая собственное доказательство полномочий.

Новая подготовка миграции закрепляет резервную идентичность в начальной политике API 3. Client открывает резервные пакеты подписанных поколений и подтверждает покрытие до переключения. Подтверждение cutover также сохраняет первое полномочие в отдельном сертификате, подписанном после вычисления отпечатков genesis и cutover. Оно связывает именно резервный ключ из закреплённого снимка. Старые контрольные точки миграции сохраняют прежний формат.

Для защищённого режима нужна несовместимая граница вступления и хранения. До переключения доверенный клиент преобразует сохранённые шифротексты и ссылки в режиме обслуживания с проверенным backup и возобновляемыми checkpoints. Корень API 2 и копии вне мигрированного хранилища сохраняют возможность расшифровки старых шифротекстов. API 2 фиксирует успешное вступление при подтверждении приглашения в `memberships.joined_at` и `invite_redemptions`. Перед выбором владельца проверить пригодность и порядок по исходному снимку. Если порядок нельзя установить, сообщить о заблокированном шаге миграции и не угадывать по дате создания профиля.

Для живого голоса нужны независимые краткоживущие секреты. Проверять фактические разрешения передачи и приёма, вместимость и активные подключения. API 2 выдаёт 60-секундный грант LiveKit и удаляет активные подключения через RPC. Для G6 проверить поведение уже выданного гранта после отключения, изменения прав и истечения в поставляемой версии LiveKit. Manager остаётся на стороне управления хостом.

Синтетические проверки AES-GCM в `tests/compatibility/protected-history.test.mjs` проверяют G1 и G2 после завершения перехода. Доставка устройствам моделируется независимыми симметричными тестовыми ключами. Публичные пакеты, окончательный формат подписей, момент публикации, откат, миграция, повторы и LiveKit остаются открытыми. Проект не выбирает новую production-зависимость.

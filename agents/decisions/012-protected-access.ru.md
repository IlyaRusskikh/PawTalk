- Для D04 право `server.edit` управляет названием и аватаром. API 3 хранит подписанный шифротекст аватара и выдаёт адресные пакеты. Client проверяет ключи устройств и полномочия автора на момент публикации по подписанным доказательствам профилей. TLS-тесты проверяют делегирование, отзыв права, подмену ключа и конфликт версии. При миграции доверенный Client владельца расшифровывает аватар API 2 и публикует его в API 3 с новым ключом. `TestProtectedMigrationHistoryTLSClient` подтверждает сохранение изображения после переключения. Нативный `--avatar-recovery` проверяет добавление резервного пакета к уже опубликованному аватару, отзыв единственного прежнего устройства и восстановление изображения на новом. В режиме восстановления Server принимает новый пакет только для устройства текущей сессии.
- Для D10 и D11 защищённый API 3 поддерживает смену собственного ника и ника участника из доступного списка. Цель определяется по эффективному профилю. TLS-тест проверяет отдельное право на свой ник, равный ранг для чужого, защиту владельца и скрытого профиля, конфликт версии, безопасный повтор и запись модераторского действия в журнале. Windows Client открывает форму из меню сервера и карточки участника. Сценарий Electron с тестовым IPC проверяет оба пути на русском и английском.
  Загруженные страницы списка и открытая карточка обновляются при изменении ников в доступной области. TLS-тест проверяет, что изменение ника за пределами канала не меняет версию его списка. Electron проверяет обновление второй страницы и карточки, а также что при прежней версии запрашивается только первая страница.
- Для UI-01 и UI-02 тесты Electron на русском и английском проверяют текстовые статусы защиты при едином цвете значков, открытие объяснения клавиатурным фокусом, наведением и нажатием, а также зелёный статус при ожидающей задаче и жёлтый во время переходного периода. Векторы `protected-text-status.test.mjs` проверяют решение по подписанному окну и ключу. Ручная проверка в браузере на Windows подтвердила различимость четырёх состояний без цвета, показ объяснения при фокусе и наведении, открытие карточки по нажатию и сохранение черновика при блокировке отправки.
- Для UI-03 `TestVisibleRotationQueueCountsCurrentTasksAcrossRestart` проверяет счётчики видимых задач и отсутствие сведений об исполнителях в ответе, в том числе после перезапуска SQLite. Electron с тестовым IPC проверяет локализованное неизвестное состояние при потере сети и отбрасывание запоздавшего ответа. Ноль появляется только после подтверждения пустой очереди.

Сценарий HIST-09 в `protected-channel-ui.cjs` проверяет открытую историю защищённого чата при потере связи и последующем отзыве. Client сохраняет только уже загруженную историю открытого окна в памяти, показывает неподтверждённый доступ и приостанавливает отправку и действия с сообщениями. После восстановления связи окно сверяет текущую границу истории и очищает отозванное содержимое. Тест проверяет очистку при полном отзыве и сохранение локального черновика без автоматической отправки. В том же сценарии HIST-04 подтверждает удаление строк и цитат до новой границы при сохранении доступа к каналу.

### Сквозные сценарии чата

- CHAT-01 и CHAT-02. `TestProtectedParticipationAndPollPermissionsTLS` проверяет обычное удаление своего сообщения в режиме только чтения и при тайм-ауте, отказ правки и отказ удаления завершённого опроса без отдельного права. Модератор без отправки удаляет сообщение владельца, а сервер отклоняет правку. Повторы не добавляют запись в аудит.
- CHAT-03 и CHAT-04. `TestProtectedParticipationAndPollPermissionsTLS` проверяет голосование и общий чек-лист в режиме только чтения, ограничения авторского чек-листа и точную границу тайм-аута. Независимые права закрытия и удаления проверены на опросе участника более высокого ранга. Анонимный итог не выдаёт личности голосовавших, а разрешённое удаление убирает обе позиции.
- CHAT-05. Нативный `--protected-pin-scope` проверяет закрепление текста, чек-листа и активного опроса. Правка обновляет закреплённый текст, удаление оригинала убирает закрепление. Поздний читатель даже с разрешением на закрепления не открывает старый оригинал. Событие меняет состояние канала без сообщения и повторного уведомления. `node apps/client/windows/scripts/server-chat-ui-smoke.mjs apps/client/windows/tests/protected-channel-ui.cjs` проверяет русские и английские состояния списка и карточки.
- CHAT-06 и CHAT-07. Нативный `--protected-attachment-scope` проверяет разные права файлов и голосовых записей, а также отказ в загрузке или привязке через чужой канал, профиль и другое устройство того же профиля. Клиент отклоняет подменённый зашифрованный блок. Используются синтетические аудиоданные.
- CHAT-08 и CHAT-09. Сервер фиксирует голоса в срок. Отдельное системное сообщение ожидает готовности живого поколения и клиента с доступом к оригиналу. Клиент открывает оригинал и текущий пакет, подписывает задачу с отпечатками источника, политики и ключа. Сервер атомарно публикует один подписанный итог, а точный повтор возвращает подтверждение. В задаче и итоговой записи есть числовой подсчёт и идентификатор оригинала. Вопрос, варианты и победители восстанавливаются в клиенте из исходного шифротекста. Поздний читатель без истории не получает задачу или итог. Сигнал WebSocket проверяется на позиции исходного опроса. `TestProtectedPollResultTasksWaitForRotationAndRespectHistory` проверяет точный срок при отключённом авторе. Нативный `--protected-poll-publication` проверяет полный Client ↔ Server после ручного закрытия во время ротации.
- CHAT-10. `TestProtectedBanCleanupKeepsBanAndRollsBackPartialDeletion` проверяет отдельный подтверждённый запрос очистки. Вызванный в середине сбой откатывает удаление и оставляет бан в силе. Точный повтор удаляет только разрешённое сообщение и пару опроса с итогом. Скрытый канал и опрос без требуемого права сохраняются.
- CHAT-11. `TestProtectedStorageQuotaPreservesArchiveAndPollPair` создаёт давление на реальное хранилище. Закрепление не защищает старую запись от очистки. Закрытый опрос и итог удаляются вместе. Клиент получает пакет и подписанную архивную цепочку по TLS, проходит через пустое живое поколение и расшифровывает оставшееся сообщение.
- CHAT-12 и CHAT-13. Нативный `--protected-mentions` проверяет обычный текст `@everyone`, отзыв массового права, запрет подменённого имени роли и точный повтор без нового оповещения. `TestProtectedMentionsAuthorizeAtMessageCommit` проверяет участника с той же ролью вне области канала. Локальное приглушение блокирует запросы массового и ролевого уведомления и сохраняет личное. Нативный тест наблюдает запросы на границе Electron Notification.

Команды CHAT-проверок завершились с кодом 0. `go test . -run '^TestProtected(PollResultTasksWaitForRotationAndRespectHistory|ParticipationAndPollPermissionsTLS|ImportedPollVotingAndDeletion|BanCleanupKeepsBanAndRollsBackPartialDeletion)$' -count=1 -v` проверяет TLS-обработчики. Нативные флаги запускались через `protected-selfhost-smoke.mjs`. В `TestProtectedMigrationHistoryTLSClient` клиент постоянного сервера после перехода на API 3 сначала видит закрытый опрос без итоговой записи, выполняет задачу и открывает подписанный результат.

### Сквозные сценарии каналов, приглашений и устройств

- UI-06 проверяется в редакторе ролей на русском и английском Electron с тестовым IPC. После конфликта при подтверждении Client загружает текущую версию по запросу пользователя, сохраняет его правки и подхватывает изменения полей, которые он не редактировал. Совпавшие поля обозначаются в форме, а применение требует нового предпросмотра. Закрытие несохранённого черновика запрашивает подтверждение.
- Для UI-04 тот же Electron-сценарий проверяет переключатель Administrator в «Расширенных правах» обычной роли и предупреждение о доступе ко всем закрытым каналам в форме и предпросмотре. У делегированного редактора без этого права раздел скрыт. `TestRosterScopesMembersAndRanksRolesAcrossPages` проверяет отдельно выбор высшей окрашенной роли и высшей роли для группы списка, когда участнику назначены несколько ролей с цветом и отдельной группой.
- Для UI-05 редактор персональных правил объясняет текущее право выбранного участника по проверенной политике канала. Electron Main требует право чтения полной политики и возвращает решение с основаниями по одному выбранному праву. IPC-тест покрывает персональное правило, ограничение полномочий и конфликт версии. На русском и английском Electron с тестовым IPC проверяет объяснение до правки и предпросмотр удаления роли, запрет которой закрывал канал.

Снимок состояния API 3 передаёт настройки только для видимых каналов. Для перенесённых каналов без подписанных настроек отображаемое имя берётся из замороженных данных API 2 после проверки видимости. Main-процесс проверяет поля, хранит сессию и возвращает отдельный формат состояния API 3 через IPC. Обычное окно показывает список и сведения о выбранном доступном канале для сервера с локально подтверждённым cutover. Тест IPC проверяет обновление истёкшей сессии и отсутствие запросов API 2. В обычном окне API 3 можно подключиться к защищённому голосовому каналу. IPC привязывает смену ключа, переподключение и выход к текущему месту и закреплённому медиашлюзу. В обычном окне подключены отправка текста и чтение сообщений текущего поколения. Main-процесс сверяет подпись с проверенной политикой и открывает пакет перед передачей текста в renderer. Повтор отправки сохраняет ID операции. Перенесённый текст с исходным архивным ключом отображается в общей ленте до новых сообщений. API 3 выдаёт подписанные доказательства поколений страницами и обратные архивные связи только при наличии полной истории и пакета текущего архивного ключа для устройства. Client проходит от текущего архивного ключа к начальному и сверяет отпечаток его подписи со связью переноса. Проверены выдача и отказ через TLS, а переход между архивными поколениями покрыт отдельным интеграционным сценарием. Лента открывает старые live-сообщения через адресный пакет устройства в текущем интервале допуска или через архив при наличии полной истории. Локальная команда `serve migration-check` читает журнал подтверждённых вступлений и инвентарь базы API 2 в одной транзакции. Она проверяет целостность SQLite и связи по внешним ключам. Если подтверждение отсутствует или два подходящих профиля имеют одинаковое самое раннее время, отчёт указывает блокирующую причину. Тесты подтверждают, что команда не создаёт отсутствующий файл, не меняет исходную базу и отклоняет уже активную защищённую схему.

Повторная подготовка принимает только архив с сохранённой контрольной суммой. Прерывание до фиксации откатывает контрольную точку и ограничение записи.

Общий контроллер передаёт проверенный архив локальному процессу Windows или контейнеру Linux без сети. Запись об успешной подготовке удерживает архив от удаления и блокирует обычный запуск и обновление. Проверка места для переноса истории и переключение схемы остаются открытыми.

Чтение истории в Go привязано к SHA-256 архива и работает с источником в режиме обслуживания. Голоса остаются в исходных таблицах. Незавершённые загрузки учитываются отдельно. Диагностика останавливает подготовку, если вложение указывает на сообщение другого канала или устройства, либо итог опроса не соответствует его автору и исходному контексту.

Обработчик миграции принимает запросы истории по TLS. Electron проверяет закреплённый сертификат хоста и подписывает одноразовый вызов действующим ключом устройства. Сервер сверяет эффективный профиль устройства с владельцем из контрольной точки в той же транзакции, где читает историю. Срок сессии API 2 не влияет на доступ мигратора. Подпись связывает сервер, устройство, ожидаемый архив и параметры страницы. Тесты Go и Node проверяют повтор вызова, исключение отозванного устройства и администратора без владения, подмену запроса и смену архива.

Обычная команда `serve` распознаёт зафиксированный источник и запускает TLS-обработчик миграции на исходном порту. Контрольная точка содержит SHA-256 файла идентичности хоста из проверенного архива. Отсутствующий или изменённый файл приводит к отказу запуска. Исходные таблицы заморожены. `/api/config` и обычная проверка доступности комнаты сообщают о режиме обслуживания. Команда сверяет снимок на диске и подтверждение работающего процесса по TLS с закреплённым сертификатом. Главный процесс Electron открывает старые сообщения, опубликованные вложения и подготовленные результаты опросов локальным ключом API 2. Получатель проверяет подпись по доверенному ключу мигратора. Локальные векторы проверяют бинарное вложение, подготовленный итог опроса и отказ при подмене.

Приём пакета доступен в режиме обслуживания по TLS. Одноразовая подпись устройства выбранного владельца связывает тип записи и хеш тела запроса. Server проверяет подпись переноса, метаданные и хеш по замороженной записи и пишет только в промежуточные таблицы. Первая запись канала закрепляет ключ первого архивного поколения для его набора данных. Для того же исходного ID повторное перешифрование возвращает квитанцию первого сохранённого пакета. Тест Go и Node проходит чтение, перешифрование и загрузку по TLS, проверяет отказ при подмене тела и ключа и повтор после переоткрытия SQLite. Ошибка записи откатывает запись целиком.

Основной процесс клиента сохраняет архивный ключ канала в защищённом хранилище ОС до отправки первой записи. При повторном вызове он сверяет SHA-256 исходного архива, проверяет сохранённые ключи и пропускает уже зафиксированные строки. Сервер возвращает для них метаданные и ID ключа без повторной передачи шифротекста. Подписанный запрос прогресса сверяет множество исходных ID сообщений, опубликованных вложений и результатов опросов со стадией импорта. Равного числа строк недостаточно. Тесты покрывают потерю ответа после commit, повторный экземпляр клиента, отсутствие или несовпадение сохранённого ключа и подмену ID при равных итогах. Публикация архивных ключей, запуск возобновления из интерфейса и переключение схемы остаются открытыми.

Выбранный владелец может запросить черновик политики для закреплённого архива. Название роли не участвует в вычислении прав. Полные администраторы API 2 перечислены отдельно как кандидаты на переход через recovery. Для владельца recovery также требуется. Неизвестные права, неоднозначный порядок рангов или несовместимые возможности блокируют выдачу применимого снимка. Например, API 2 показывает список каналов участнику без `chat.read`, а в новой схеме `channel.view` тоже разрешает чтение новых сообщений. Публикация подписанной политики и зачисление получателей ключей остаются открытыми.

Client создаёт код восстановления локально и доказывает владение двумя независимыми ключами. Интеграционный тест Go и Electron-транспорта проверяет отказ при повторном использовании запроса, несовпадении архива и попытке заменить ключи. Готовность восстановления зависит от записи и проверки зашифрованных пакетов.

Для ключа импортированной истории Client шифрует резервный пакет на публичный ключ восстановления, локально открывает пакет и сверяет отпечаток секрета перед подписью подтверждения. Server принимает пакет с подписями действующего устройства владельца и резервной идентичности. Он сверяет канал и отпечаток с закреплённым ключом и возвращает квитанцию первой записи при повторе. Черновик политики показывает число закреплённых ключей архива и число подтверждённых пакетов. Открыты выдача пакетов при восстановлении, пакеты актуальных ключей и активация.

Возобновление резервирования запрашивает у Server страницы ключей без подтверждённого пакета. Client заново проверяет код и использует ранее сохранённый локальный ключ с совпадающим отпечатком. После потери ответа повторный запуск пропускает записанный пакет и сверяет покрытие с фактическим набором закреплённых ключей. Покрытие закреплённых ключей относится только к архиву и не меняет готовность восстановления в черновике политики.

Команда хоста `serve migration-verify <archive-sha256>` читает один снимок SQLite, сверяет checkpoint и ключевую идентичность хоста, проверяет внешние ключи и точное покрытие импортом. Она пересчитывает отпечатки сохранённых шифротекстов, проверяет их подписи и происхождение, повторно проверяет подписи резервных пакетов и выдаёт отпечатки истории, пакетов и черновика политики. Открытые блокировки политики перечислены в отчёте. Команда работает до подписанной активации и не меняет состояние миграции.

Позиции для правил доступа считаются последовательно внутри каждого канала по исходному порядку сообщений. Старые идентификаторы остаются точными и используются для связей. Черновик политики показывает первую свободную позицию каждого канала, а `migration-verify` включает отдельный отпечаток соответствия исходных идентификаторов и позиций. Тесты покрывают независимый порядок каналов и идентификаторы за пределами безопасного диапазона JavaScript.

Отчёт завершённого импорта содержит `reviewDigest`, когда черновик политики без блокировок, резервная идентичность владельца зарегистрирована и все закреплённые ключи архива покрыты подтверждёнными пакетами. Внутренний транспорт Client подписывает этот отпечаток после явного подтверждения и запроса политики через закреплённый TLS. Хост принимает подтверждение через stdin команды `serve migration-approve-import <archive-sha256>`. Команда заново проверяет подпись действующего устройства владельца и пересчитывает отпечатки в одной транзакции записи. Повтор с тем же отчётом возвращает исходную квитанцию. Подтверждение импорта оставляет сервер в режиме обслуживания до готовности актуальных ключей и подписанной активации.

Подтверждение импорта в той же транзакции записывает индекс истории по каналу и позиции. Повтор сверяет индекс с подписанным отпечатком. Внутреннее чтение возвращает исходный ID, шифротекст и подпись миграции. Оно использует текущий ACL и интервал допуска под той же блокировкой доставки, что и события. В тесте владелец читает обе страницы, а новый участник с видимостью канала без права полной истории получает пустую страницу. Инициализация защищённой политики и задач ротации может выполняться в транзакции переключения. Тест откатывает создание политики целиком. Публичная выдача истории и активация остаются открытыми.

Первое устройство владельца регистрирует отдельный X25519-ключ получателя после подтверждения импорта. Client сохраняет закрытый ключ в защищённом локальном хранилище до отправки запроса. Server проверяет владение ключом по одноразовому запросу, связывает регистрацию с подписью действующего устройства и отпечатком одобренного импорта. Отчёт `migration-verify` повторно проверяет сохранённую подпись и показывает публичный ключ получателя. Этот ключ нужен для подготовки пакетов начального защищённого состояния. Пакеты и переключение ещё открыты.

Отчёт `migration-verify` выдаёт начальный снимок с зарегистрированным ключом получателя владельца. Client воспроизводит снимок из черновика политики, проверяет совпадение ключа с локальным хранилищем и подписывает снимок и его связь с подтверждённым импортом. Команда хоста `serve migration-stage-policy <archive-sha256>` принимает подписи через stdin и атомарно сохраняет начальную политику, доказательство и задачи ротации. Повтор возвращает то же доказательство. Сервер остаётся в режиме обслуживания до подготовки ключевых пакетов и подписанного переключения.

После закрепления начальной политики Client может подготовить первые поколения live и archive для текстового канала в режиме обслуживания. Server принимает только одноразовые запросы от зарегистрированного устройства владельца, привязанные к архиву и подписи начальной политики. Используются те же задачи ротации, подписи, HPKE-пакеты и обратные ссылки, что и в ядре защищённого режима. Client повторно открывает выданные пакеты и сверяет отпечатки.

Client создаёт резервный пакет для каждого начального live- и archive-ключа, открывает его локально и подписывает подтверждение резервной идентичностью. Server сверяет пакет с подписанным поколением, назначением ключа и начальной политикой. `migration-verify` проверяет сохранённые подписи и выдаёт отпечаток покрытия после подтверждения всех комплектов для текстовых каналов. Интеграционный тест возобновляет работу после потери ответа о записи live-поколения и о записи резервной копии.

Для импортированного канала Client шифрует ключ старой истории под начальным архивным ключом и подписывает связь. Server сверяет её с закреплённым ключом импорта и подписанным архивным поколением. Client проверяет связь, открывая её после записи и при повторном запуске. Отчёт проверяет полноту связей. Внутренняя выдача сверяет текущую регистрацию устройства, видимость канала и право полной истории под блокировкой доставки. Отзыв этого права прекращает выдачу связи даже при сохранённой видимости канала. Подключение выдачи к рабочему API и подписанное переключение остаются открытыми.

`migration-verify` выдаёт отпечаток для переключения после повторной проверки индекса истории, начальных пакетов устройств, обратных ссылок, резервных копий и связей импортированной истории. Незавершённые задачи ротации удерживают отчёт в ожидании. Client подтверждает отпечаток и привязанную к нему начальную политику. Команда `serve migration-approve-cutover <archive-sha256>` принимает подпись через stdin, заново сверяет данные в транзакции и сохраняет разрешение. Повтор возвращает ту же квитанцию. Запись разрешения сохраняет режим обслуживания до подключения рабочего API 3.

Отдельный обработчик API 3 открывается на мигрированной базе после проверки подписанного разрешения. Вход по TLS использует одноразовый запрос, привязанный к серверу, отпечатку переключения, экземпляру процесса и устройству. Server хранит хеши токенов отдельно от замороженных сессий API 2 и проверяет актуальную политику на каждом запросе. Обработчик отдаёт видимые каналы, страницы импортированных сообщений и защищённую связь с ключом истории. Интеграционный тест Go и Electron читает и расшифровывает импортированное сообщение, отклоняет повтор подписи и устаревший токен, а также проверяет отказ устройству без ключа получателя. Оставшиеся рабочие маршруты перечислены в карте этапов.

Обработчик API 3 также выдаёт текущий пакет ключа только его получателю и принимает новые зашифрованные текстовые сообщения. Выдача ключей и история учитывают текущие права и блокировку доставки. Client шифрует текст локально, подписывает контекст отправки и после потери ответа повторяет ту же операцию. Интеграция проверяет продолжение нумерации после импортированных сообщений, повтор без дубликатов, расшифрование нового текста и отказ устройству без ключа. Старое сообщение открывается через полученный по API архивный пакет и зашифрованную связь.

API 3 принимает предпросмотр и подписанное применение изменений ролей, категорий, каналов и ACL. Предпросмотр связывает условия операции с предыдущим доказательством и отпечатком результата. Client сверяет намерение и воспроизводит полный снимок для владельца перед подписью. Server заново проверяет полномочия и применяет изменение при совпадении версии. Полные страницы доказательств доступны владельцу. Интеграция покрывает смену роли, редактирование ACL, отказ неуполномоченному участнику и конфликт двух предпросмотров. Выдача доказательств с учётом видимости для делегированных участников остаётся открытой.

В обычном окне API 3 владелец может создать канал, изменить его настройки, скопировать настройки, удалить канал, изменить правило роли и синхронизировать права с категорией. Основной процесс отдаёт окну настройки и правила ролей выбранного канала. Остальные правила сохраняются при изменении. Предпросмотр проверяется до показа и остаётся в основном процессе. Применение использует одноразовый идентификатор, привязанный к серверу и сессии. Сценарий в Electron проверяет доступность действий по роли, раздельное подтверждение и геометрию диалога на русском и английском. Серверные операции проверяются отдельными TLS-тестами.

Редактор владельца создаёт и удаляет роли, меняет их права, порядок, название, цвет, значок и признаки отдельного отображения и упоминания. Оформление хранится в подписанной политике по неизменному ID роли. Для ещё не переименованной перенесённой роли окно использует имя из замороженных данных API 2. Подписанные изменения оформления требуют `role.edit` и соблюдают иерархию. Проверены сохранение прав и порядка при переименовании через TLS и подтверждение в Electron.

Список текстового канала включает допущенных участников независимо от наличия активной сессии. Для каждого участника применяется цвет его высшей роли с цветом и группа его высшей роли с отдельным отображением. Карточка показывает все роли участника. Для общего списка сервер проверяет `member.list`. Каждая страница повторно проверяет допуск, а продолжение привязано к ревизии политики. Проверки Go покрывают ограничение области и группировку между страницами, TLS проверяет отказ после отзыва и устаревшую страницу, Electron проверяет отображение в обеих локализациях.

Назначения ролей и персональные правила канала используют выбор действующего участника. Имена перенесённых профилей берутся из замороженных данных, а цели операций определяются ID подписанных профилей. Для назначения отправляется изменение только выбранного профиля. Для персонального правила сохраняются остальные правила канала. После проверки предложенного снимка в основном процессе предпросмотр показывает изменение числа видимых каналов и каналов с полной историей. Проверены отказы для базовой роли и персонального правила владельца, подтверждение в Electron и снятие роли через TLS без изменения оформления или чужих назначений. Целевые проверки UI делегированных прав остаются открыты.

Владелец может создать, переименовать и удалить категорию, изменить её ролевые и персональные правила, создать канал в категории или перенести существующий. Перенос предлагает сохранить эффективные правила или принять правила назначения. Предпросмотр перечисляет изменения видимости и доступа к истории и отмечает текстовые каналы, которым потребуются новые ключи. Удаление категории отдельно предлагает оставить каналы с действующими правами или удалить вместе с ней. Состояние API 3 раскрывает категорию только при наличии видимого дочернего канала. Подтверждённое устройство может получить эти метаданные в ожидании первого пакета ключей. Проверены оба режима переноса, сохранение доступа при удалении категории и фильтрация через TLS.

Порядок каналов и категорий сохраняется в подписанном снимке. Операция указывает элемент, соседний ориентир и сторону. Сервер сверяет право редактирования обоих элементов, меняет только доступную для редактирования последовательность и сохраняет позиции скрытых и недоступных для редактирования элементов. Публичный список отдаёт только разрешённые элементы в итоговом порядке. Копирование создаёт новую категорию с собственным ID, заданным названием и копией правил, оставляя каналы в исходной категории. Проверены TLS, перестановка с недоступными элементами и диалоги Electron. Делегированное подписание в обычном интерфейсе открыто.

Интеграция отклоняет пропущенное доказательство, подставленную текущую ревизию и изменённую границу. Новая миграция закрепляет v3 с первой ревизии. Ранее подготовленные миграции продолжают вычислять начальную политику в закреплённом формате.

Открытая лента проверяет начало доступной истории в API 3, в том числе до загрузки следующей страницы. TLS-сценарий проверяет изменение границы с сохранением допуска. Electron проверяет очистку ленты с незагруженными страницами и возврат черновика.

API 3 удаляет обычные сообщения по каналу и исходной позиции. Сервер проверяет допуск к оригиналу и эффективного автора в транзакции. Для собственного сообщения достаточно сохраняющегося допуска, в том числе в тайм-ауте. Для чужого требуется `message.delete-other` независимо от права отправки и ранга автора. Удаление исключает новый шифротекст из ленты и скрывает перенесённый оригинал, сохраняя неизменный снимок миграции. Квитанция отправки остаётся, поэтому повтор не создаёт сообщение заново. Для перенесённого завершённого опроса действует `poll.delete-completed`. Сервер повторно проверяет право и доступ к исходной позиции, в одной транзакции скрывает опрос и связанный опубликованный результат, очищает их закрепления и пишет одну запись аудита. Повтор возвращает успех без новой записи. В Client действие доступно у опроса при наличии отдельного права.

Client показывает вопрос и варианты новых и перенесённых опросов из проверенного шифротекста. Создание требует Send и `poll.create`. Сервер сохраняет параметры голосования, исходную позицию и квитанцию вместе с сообщением. Дедлайн отсчитывается от принятия сообщения. Сервер проверяет право `poll.vote`, тайм-аут и историю по исходной позиции. Голосовать и отзывать голос можно без Send. Новые бюллетени хранятся поверх замороженного источника, квитанция не позволяет повтору изменить более поздний выбор. Сервер отклоняет новые голоса с момента дедлайна, соблюдает правила показа промежуточного итога и не выдаёт личности в анонимном опросе. Удаление завершённого нового опроса также требует отдельного права.

Автор с правом Send может завершить опрос досрочно. Для чужого опроса действует `poll.close-other` в доступном канале без сравнения рангов. Server фиксирует время и числа голосов в одной транзакции с записью аудита ручного завершения. Фоновая обработка в постоянном Server сохраняет итоги по дедлайну без онлайн-автора, включая опросы без ручного закрытия.

Системное сообщение с итогом получает отдельную позицию. Server подписывает агрегированные числа, время, канал, обе позиции и отпечаток исходного пакета своим проверяемым ключом. В подписанном результате нет текста вопроса, вариантов и личностей голосовавших. Client проверяет подпись и строит отображение из доступного зашифрованного оригинала. Такой формат позволяет публиковать уже зафиксированные итоги после перезапуска без ожидания клиентских ключей. Уникальная связь с опросом предотвращает повторную публикацию. Удаление, закрепления и доставка применяют границу исходного опроса.

Карточка открытого опроса показывает имена голосовавших, когда доступен подсчёт. Server передаёт только профили из текущей области участников канала. При исключении профиля из этой области его имя исчезает, а голос остаётся в сумме. Анонимный опрос выдаёт только разрешённые числа и свой выбор. Для имён используется тот же источник, что и для списка участников канала.

Перенесённый результат наследует границу исходного опроса. Server применяет её к ленте, прямым старым ID, закреплениям, ссылкам ответов, изменениям ленты и делегированному аудиту. После сужения истории Client убирает уже показанный результат и цитаты на него. Проверка с границей между вопросом и итогом использует синтетический снимок допусков. Отдельная проверка подтверждает, что обычная пагинация после вопроса сохраняет доступ к итогу.

В защищённой ленте доступны вложения, перенесённые из API 2. Server выдаёт шифротекст блоками до 1 МиБ и сверяет канал, исходную позицию, привязку файла и действующий допуск под блокировкой доставки. Client проверяет подписанный пакет и привязку к расшифрованному сообщению, затем снова проверяет оригинал перед передачей файла в окно. При уходе оригинала из ленты окно освобождает локальные ссылки на загруженные данные.

Для новых вложений Server принимает блоки шифротекста до 1 МиБ и привязывает завершённые загрузки к сообщению в транзакции отправки. Подпись сообщения связывает упорядоченные ID и типы вложений. Загрузка и отправка отдельно проверяют текущее право на файл или встроенное голосовое сообщение. Незавершённая загрузка закреплена за устройством, действующим профилем и каналом. Опубликованные данные выдаются по позиции исходного сообщения и удаляются с ним.

Защищённый редактор позволяет выбрать файлы или записать голосовое сообщение в зависимости от разрешений. Основной процесс Electron шифрует каждый файл отдельным случайным ключом AES-GCM. Имя, тип, размер и ключ доступны из подписанного зашифрованного сообщения. Для видео Client локально выбирает кадр и шифрует его отдельным ключом. Видео и миниатюра привязаны к одной позиции истории в транзакции отправки. Перед выдачей байтов в окно Client проверяет привязку, аутентичность шифротекста и доступ к исходному сообщению. Интеграционный тест Go и Electron по TLS покрывает потерю ответа на блок, загрузку в несколько блоков, повреждение шифротекста, открытие миниатюры и отказ после удаления оригинала. Нагрузочная приёмка остаётся открытой.

Поиск и галерея читают страницы доступной истории, включая импортированные сообщения и доступные редакции. Основной процесс Electron применяет поисковый запрос к расшифрованным данным локально. Галерея открывает вложения по позиции оригинала через проверяемую выдачу файлов. Продолжение просмотра сверяет границу истории и позицию журнала изменений. Открытие результата заново проверяет исходное сообщение. При изменениях окна истории интерфейс очищает старые результаты и ссылки на превью.

В защищённом редакторе `@` открывает список доступных в канале профилей, представленных ролей и разрешённых массовых упоминаний. Фильтрация выполняется на клиенте по страницам списка, а выбор сохраняет ID и диапазон в черновике. Server сверяет текущее право `mention.mass` для `everyone` и `online`, свойство `Mentionable` или право `mention.any-role` для роли и видимость канала для адресата по ID профиля. Проверка, запись сообщения и создание уведомлений для подходящих адресатов выполняются в одной транзакции. Подпись и дополнительный контекст AES-GCM связывают сообщение с хешем адресатов и случайной солью. История содержит хеш, а адресаты и позиции в тексте восстанавливаются и сверяются после расшифровки.

Защищённая очередь выдаёт только ссылки на оригиналы в текущем допуске получателя. Непрозрачный курсор привязан к профилю. Очередь хранит уведомления 30 секунд и удаляет их вместе с оригиналом. Для `@online` сервер использует опрос очереди с допущенного устройства за последние 25 секунд. Личное упоминание имеет приоритет, если получателя одновременно адресовали группой.

Electron опрашивает очередь в фоне и повторно сверяет версию оригинала и право получателя перед отображением системного уведомления. Клиент закрывает активное уведомление при следующей проверке после отзыва доступа, удаления, новой редакции или истечения срока. Локальный mute подавляет звуки и системные уведомления для массовых и ролевых упоминаний. Личные упоминания сохраняют прежнее исключение из mute, а deafen подавляет звук.

API 3 создаёт, выдаёт списки и отзывает приглашения отдельно от API 2. При создании устройство подписывает ID приглашения, хеш публичного ключа приглашения, параметры использования и текущий хеш политики. Server проверяет подпись и разрешение в транзакции записи. Повтор с теми же данными сохраняет первый срок и лимит. По умолчанию приглашение действует 24 часа и допускает одно вступление. Список содержит метаданные, а проверочный хеш и подпись не выдаются. Права просматривать и отзывать чужие приглашения проверяются отдельно.

Окно «Приглашения» в меню сервера использует разрешения из актуального состояния API 3. В нём можно задать срок из списка или выбрать дату вручную, ограничить число вступлений или снять числовой лимит до истечения срока. Копирование ссылки доступно сразу после её создания. Постраничный список показывает срок, число вступлений и доступность отзыва.

Electron подписывает создание по актуальной вершине политики. Ссылка API 3 передаёт ключ самого приглашения во фрагменте URL вместе с отпечатком TLS и параметрами доверия к переносу. При вступлении клиент сверяет сертификат и подписанную конфигурацию до передачи доказательств. Защищённое локальное хранилище сохраняет ключ согласования устройства и данные повтора заявки до первого запроса. Секрет приглашения в реестр не попадает. После квитанции сервер появляется в списке Windows Client. Пока действует ограниченная сессия, экран показывает ожидание защищённого доступа и при подключении повторяет попытку открыть обычную сессию.

При приёме приглашения три подписи связывают его публичный ключ, новый профиль, устройство и ключ согласования с сервером и конкретным переносом. Закрытый ключ приглашения остаётся у получателя ссылки. Server проверяет подпись создателя по политике выпуска, срок и отзыв. Квитанция, расход использования, подписанный переход `member.redeem` и задачи ротации фиксируются в одной транзакции. Повтор того же запроса возвращает исходную квитанцию. Запись принятия хранится отдельно от замороженных таблиц API 2.

Доказательство включает исходную подпись приглашения, редакцию политики выпуска, срок, лимит и время принятия. Server и Electron независимо проверяют подписи и право выдавшего приглашение устройства по исторической политике. Если редакция выпуска отсутствует в текущей странице доказательств, Electron восстанавливает подтверждённую часть цепочки от закреплённого якоря. Подгруженный снимок связывается с ранее проверенным хешем. Цепочка учитывает лимит автоматических зачислений. Подпись идентичности Server фиксирует переход, а вычисляемое изменение ограничено профилем с правами `@everyone`, устройством и получателем ключей. Тест проверяет отказ при попытке назначить роль через такой переход даже при действительной подписи Server.

Зачисленный участник открывает обычную сессию и видит доступные каналы сразу. Для текстовых каналов статус показывает ожидание пакетов текущих поколений. Ротация при зачислении доступна подходящему исполнителю без приоритета за новичком, у которого ещё нет предыдущего пакета. Сквозной TLS-сценарий проверяет получение живого и архивного пакетов после подключения владельца. Доставка без его аттестации политики остаётся открытой.

Для добровольного выхода устройство подписывает запрос, привязанный к текущей вершине политики. Переход `member.leave` прекращает членство, сбрасывает роли, отзывает устройства и завершает их сессии в одной транзакции. Электронный клиент сохраняет точный запрос до отправки и может повторить его после потери ответа. Повтор уже совершённого выхода возвращает квитанцию, сохраняя более позднее членство. При новом вступлении тот же профиль и устройство получают базовые права по новому приглашению и свежий ключ согласования. Публичный ключ подписи остаётся доступным для проверки старых доказательств, ключи получателей и прежние токены остаются отозванными. Владелец сохраняет членство до передачи владения.

Принятое устройство может открыть ограниченную сессию отдельным доказательством владения ключом. Её токен позволяет прочитать только собственную квитанцию и состояние ожидания ключей. При чтении Server заново проверяет подписи из записи принятия, исходное приглашение и действующие ограничения. Токен ограниченной сессии теряет силу после перезапуска runtime и действует только на маршруте квитанции.

Подписанный переход `member.admit` проверяет право автора перехода и точное совпадение подписанного запроса с принятой квитанцией в транзакции. Он добавляет профиль с базовыми правами `@everyone`, устройство и получателя ключей. Go проверяет переход при восстановлении цепочки политики, Electron сверяет три подписи заявителя и привязку к переносу. После перехода обычная сессия проверяет владение ключом из квитанции, действующие ограничения и принадлежность устройства активному профилю по подписанной политике. При обновлении временной таблицы сессий перезапуск отзывает старые токены, как и при обычной смене привязки runtime. Устройства из API 3 хранятся отдельно от замороженных таблиц API 2. Тест проверяет видимое состояние через обычный маршрут, отказ до включения в политику, раздельную область токенов, отзыв обычной сессии и воспроизведение подписи отозванного устройства.

Перенесённые и новые чек-листы отображаются в защищённой ленте. Название и тексты пунктов Client извлекает из проверенного шифротекста. Новый список требует Send и `checklist.create`. Сервер сохраняет его вместе с сообщением и квитанцией в одной транзакции. Подпись и шифротекст привязаны к порядку ID пунктов и правилу участия. Изменение отметок требует `checklist.check` и допуска по правилу списка, работает без Send и запрещено в тайм-ауте. Отметки сохраняются отдельно от исходного снимка. Повтор принятой операции возвращает текущее состояние и сохраняет более поздние изменения. Автор редактирует список с правом Send через тот же протокол редакций и с той же границей истории, что у обычного сообщения. При публикации редакции сервер сохраняет отметки оставшихся ID и очищает удалённые в одной транзакции. Текстовая правка не может изменить тип списка.

Закрепления API 3 хранят ссылки на исходные позиции живых и перенесённых сообщений. Сервер проверяет доступ к оригиналу и единое право `message.pin` при закреплении и откреплении. Выдача постраничная и ограничена текущим интервалом истории. Открытие закрепления использует обычную проверку и расшифрование сообщения, включая новую редакцию, и повторно проверяет ссылку перед выдачей текста. Удаление оригинала очищает закрепление в той же транзакции. TLS-тесты проверяют закрепление чужого сообщения без Send, чтение правки и перенесённого оригинала, отказ за границей истории и очистку после удаления. Electron проверяет открытую карточку при правке и сужении истории. Приёмка общей очистки под нагрузкой остаётся открытой.

Новые ответы в защищённом чате ссылаются на исходную позицию сообщения в том же канале, в том числе перенесённого. Сервер проверяет оригинал в транзакции отправки и выдаёт позицию вместе со случайным значением для проверки ссылки, пока читателю доступен сохранённый оригинал. Подпись и шифротекст ответа подтверждают криптографический отпечаток ссылки. Обычный текст сохраняет прежний формат пакета. Client строит цитату по доступной ленте и убирает её, когда оригинал покидает ленту. При отзыве доступа выбранная цитата сбрасывается, а собственный неотправленный текст сохраняется.

При переносе ответа API 2 Client заново шифрует сообщение, сохраняя ID оригинала и убирая скопированные текст цитаты и имя автора. Исходная резервная копия и отпечаток сохраняют происхождение данных API 2. При чтении основной процесс сопоставляет подтверждённые подписью старые ID с позициями на текущей странице или запрашивает их в индексе переноса в пределах доступной истории канала. Удалённый, отсутствующий и недоступный оригинал дают одинаковую отметку в цитате. Ранее подготовленные пакеты можно читать. Client игнорирует сохранённые в них поля предпросмотра.

Общесерверный тайм-аут применяется к эффективному профилю. Сервер проверяет `member.timeout` и строгую иерархию при назначении. Снятие использует то же право, включая снятие с себя. Абсолютный срок от 1 минуты до 28 дней начинается в транзакции изменения, которая также сохраняет причину, исполнителя и квитанцию повтора. Операционный тайм-аут хранится отдельно от подписанных ролей и состава получателей, поэтому чтение и доступ к истории сохраняются. Отправка проверяет срок в транзакции, а голосовые места и ключевой обмен затронутых каналов отзываются при назначении. Отключение активного участника повторяется до ответа медиасервера. Участник видит причину и срок, а управляющий может выбрать готовую длительность или ввести свою.

Кик и бан требуют действующей сессии, права, более высокого ранга и причины. Подписанный переход сбрасывает роли, отзывает устройства и закрывает сессии. Бан блокирует новый допуск эффективного профиля до указанного срока или снятия. Снятие требует `member.ban` без сравнения с рангом автора ограничения. Истечение и снятие оставляют профиль вне состава, для повторного вступления нужна действующая ссылка. Карточка участника показывает доступные действия, список блокировок доступен управляющим. Цель получает причину и срок при следующей проверке сессии. Действующие баны API 2 появляются в общем списке по эффективному профилю. Подписанное снятие учитывает связанные профили и сохраняется после повторного вступления. Исходные строки API 2 остаются замороженными.

При кике или бане Client по умолчанию сохраняет сообщения. Можно выбрать час, сутки, семь дней или всю доступную историю. Предпросмотр показывает число записей без списка каналов. API 3 проверяет видимость, позицию оригинала и право удаления каждой записи, включая отдельное право для завершённого опроса и связанного результата. После подписанного кика или бана Server повторно сверяет набор и применяет очистку отдельной транзакцией. Client показывает её результат отдельно. Проверены граница истории, скрытый канал, оба вида прав на удаление, выборка импортированных позиций и сохранение бана после отказа очистки.

Журнал API 3 и окно Client используют отдельное право `audit.view`. Зафиксированные изменения ролей, устройств, каналов и категорий, тайм-ауты и обычные удаления добавляют записи в той же транзакции. Аудитор с делегированным правом видит серверные действия и только доступные ему каналы и интервалы истории. Записи категории доступны, если виден хотя бы один её канал. Владелец и Administrator также видят записи удалённых ресурсов. Записи содержат типизированные метаданные действий, без текста сообщений, криптографических пакетов и приглашений. По умолчанию срок 365 дней. Подтверждённое сокращение очищает просроченные записи, оставляя отдельные хранилища политики и ключей. Тексты причин предыдущих квитанций тайм-аута переносятся в журнал, а квитанции сохраняют отпечаток запроса. Тест очистки проверяет точную границу 365 дней и сохранность доказательства политики, архивной связи и пакетов восстановления. Курсор из потерянной области доступа отклоняется.

Рабочий API 3 выдаёт до четырёх доступных задач ротации за проход. Сервер фиксирует право исполнения, затем повторно сверяет политику и назначение перед выдачей состава. Для архивной задачи требуется наличие исходных пакетов у устройства. Целевые пакеты выдаются группами до восьми под действующим назначением. Основной процесс Electron обрабатывает задачи при фоновом подключении после проверки политики. При потере ответа о записи он сверяет подписанное поколение с отправленным результатом. TLS-интеграция проверяет этот повтор, запрет выдачи архивных пакетов ограниченному участнику и выполнение live-ротации участником после истечения приоритета инициатора. Фоновый клиент с узкими доказательствами подхватывает live-задачу и сверяет подписанное поколение после имитации потери ответа. Тот же TLS-стенд проверяет архивную ротацию с узкими доказательствами и отказ при отсутствии доказательства подписанта целевого пакета. Для обеих ротаций корень политики с отпечатками списков ротации подтверждён владельцем. Для предпросмотра `channel.order` обычный участник с правом `channel.edit` проверяет исходный и опорный каналы по подтверждённой политике v7. API 3 сохраняет подписанную перестановку без изменения ревизии политики. TLS-тест покрывает сохранение скрытой позиции, отказ при подмене подписи или устаревшем основании и повтор квитанции. Интерфейс делегированной перестановки доступен в обычном окне Windows. IPC передаёт только ID предпросмотра для подтверждения. Electron проверяет выбор опорного канала, сохранение, обновление списка и отзыв права в обеих локализациях. Из журнала аудита Client проверяет подпись конкретной перестановки и исторические полномочия автора. TLS-тест отклоняет подмену операции и проверяет одинаковый ответ для скрытого и отсутствующего доказательства. Полная проверка опубликованного порядка остаётся открытой.

Команда хоста `serve migration-activate <archive-sha256>` проверяет разрешение и атомарно записывает исходные обязательства, таблицу сессий и версию активного формата. Обычный запуск постоянного Server выбирает рабочие маршруты API 3 для активной базы. При повторном запуске он проверяет подпись разрешения и цепочку политики от исходного снимка до текущей версии. Интеграция покрывает откат при сбое записи, сохранение более поздних подписанных изменений после перезапуска и отказ API 2 открыть активную базу. Полный набор сценариев API 3, в том числе голос и восстановление, ещё открыт.

Встроенный хост предлагает создание защищённой комнаты API 3. Electron независимо проверяет исходную политику, подписывает её ключами владельца и подтверждает идентичность временного Go Server по закреплённому TLS. Ключи подписи и расшифрования остаются в Client. Server включает рабочие маршруты после сохранения исходной политики и поканального подтверждения. Временный и постоянный Server используют одинаковые фоновые обработчики. Изолированный прогон Electron, Go и локального LiveKit подтверждает запись и чтение зашифрованного текста, ротации живого и архивного ключей и чтение старого сообщения гостем с полной историей. API 2 выбирается отдельно при создании совместимой комнаты.

Владелец и приглашённый участник с Connect подключаются к LiveKit с E2EE. Client гостя проверяет актуальное подтверждение v8 и доказательство допуска каждого устройства в голосовом составе. В трёх изолированных прогонах оба Client декодировали синтетический звук друг друга. Подмена доказательства отклоняется до публикации пакетов ключа. Гостевой прогон запрещает запрос полного снимка. Аппаратная и внешняя сетевая приёмка остаются открытыми.

Общий сценарий подписанной миграции проходит в Linux Compose и нативном Windows Manager. Он проверяет импорт, архивные и резервные пакеты, переключение на API 3, закреплённый TLS и расшифрование перенесённого сообщения после перезапуска. Обычное восстановление отклоняет архив API 2 поверх активного API 3 до остановки комнаты, исходная копия сохраняет SHA-256. Отдельный Windows-сценарий проходит от read-only проверки SQLite до подготовки, повтора квитанции после перезапуска и явного отката. Windows-тесты используют Go host, Server и Electron Client с DPAPI. Регистрация и статус службы SCM моделируются.

Действующий участник может подписать регистрацию или замену резервной идентичности через API 3. Сервер проверяет обе подписи и доказательство согласования ключей, принимает ровно одну операцию на текущем основании и возвращает квитанцию без снимка политики. Замена отзывает старые ключи и ставит задачи ротации доступных поколений. Тесты проверяют просроченный запрос, повтор принятой квитанции, отзыв при бане и воспроизведение подписанной цепочки в Go и Client.

Client локально открывает актуальные пакеты, подписывает доказательства открытия и отправляет их одним запросом. Server сверяет подписи и точный состав актуальных поколений и записывает готовность в той же транзакции. Проверены ротация между получением пакетов и подтверждением, потеря квитанции и назначение роли Administrator после подтверждения. Интерфейс назначения ролей показывает имена участников, которым ещё нужна настройка восстановления.

Окно Windows создаёт переносимый набор с кодом и закреплённой идентичностью сервера до регистрации и принимает его при входе после потери устройств. Операция сохраняет эффективный профиль, текущие роли и ограничения, отзывает старые устройства, сессии API 3 и голосовые гранты и планирует ротации. Нативный прогон проверяет отказ для прежнего кода, точный повтор после потери квитанции и восстановление архива на новом устройстве единственного владельца.

Новое устройство владельца подписывает аттестации v2 после проверяемого перехода полномочий. Сквозной сценарий на временном хосте проверяет, что гость продолжает пользоваться поканальными доказательствами и открывает свой архивный пакет. В новой миграции код регистрируется в начальной политике API 3, а отдельное полномочие подписывается при подтверждении cutover. TLS-проверка постоянного Server восстанавливает владельца с исходным кодом сразу после перехода и после редактирования истории и ротаций. Исходные таблицы API 2 остаются замороженными. Старые контрольные точки сохраняют прежний формат.

Передача владения использует подписанное предложение с ограниченным сроком и основанием политики. Только выбранный действующий участник с готовым восстановлением может принять его с одного из подтверждённых устройств. Принятие записывает смену владельца, пересчитывает допуск и планирует обновления ключей одной транзакцией. Назначенные роли обоих профилей сохраняются. Поканальный получатель сверяет подписи прежнего подписанта и устройства нового владельца и доказательство принадлежности устройства к согласованному набору. В Windows Client прежний владелец может отозвать предложение, а получатель подтверждает принятие отдельно. Пары Go и Electron проверили неподготовленное восстановление, отмену, повтор после потери квитанции, недоступность полного снимка прежнему владельцу и проверку им аттестации v2 нового владельца.

Обычная привязка добавляет новое устройство в существующий профиль по подписанному `device.bind`. Устройства обмениваются карточками и сравнивают короткий код перед одобрением. Новое устройство доказывает владение своим signing-ключом и отдельным X25519-ключом. Одобрение привязано к действующему устройству и голове политики. Нативный Electron-тест через закреплённый TLS проверяет отказ до одобрения, потерю ответа после записи, сохранение обеих сессий, чтение архива и отправку с нового устройства. Интерфейс RU/EN отдельно проверен с синтетическим IPC.

Новая подписанная отвязка сохраняет одноразовое разрешение на привязку устройства, которое было действующим в отделяемом профиле. Повтор требует подписи этого устройства и подтверждения действующего устройства основного профиля. Бан и отзыв при восстановлении сохраняют силу. Client хранит новый X25519-ключ отдельно до проверки квитанции и подписи подтверждающего устройства. Нативный тест проводит отвязку, перезапуск между созданием заявки и завершением, подмену подписи квитанции и повтор после успешного завершения. Он также проверяет завершение уже одобренной привязки, если за это время основным стал другой профиль, а зарегистрированный ключ остался у того же устройства. Для отвязок, записанных более ранней сборкой без явного разрешения, доступно новое вступление по приглашению.

Для двух действующих профилей API 3 окно предварительного просмотра показывает выбранный основной профиль, роли обоих профилей и число переносимых устройств. Оба устройства подписывают один запрос с ID профилей и устройств, сроком и головой политики. Server применяет `profile.link` атомарно с отзывом прежних сессий переносимых устройств. Заново открытая сессия использует основной профиль, а старые приглашения сохраняют исходного автора и проверяются по политике выпуска. `profile.unlink` отзывает сессии и ключи отделяемых устройств. Go TLS и нативный Electron проверяют двустороннее согласие, отсутствие объединения ролей, смену эффективного профиля и отзыв при отвязке. Go TLS отдельно проверяет новое вступление отделённого профиля с базовыми правами.

При `scope.device` нынешний подписант выбирает действующее устройство владельца. Это устройство проверяет и подтверждает карточку. Подписанный переход привязан к голове политики и к предыдущему полномочию подписи. Нативный Electron через закреплённый TLS проверяет повтор после потери ответа, отказ прежнему подписанту при попытке публикации и проверку текущего доступа гостем по v2, включая обратную передачу исходному устройству. В отдельном нативном сценарии владелец принимает владение со связанного устройства, передаёт подпись устройству основного профиля и отвязывает прежнее устройство. Прежняя сессия отзывается, а гость проверяет новую аттестацию и допуск к каналу. Окно отвязки текущего подписанта открывает передачу подписи.

Новый формат замороженного источника API 2 переносит связи профилей и происхождение устройств в подписанную начальную политику. Ранее созданный источник без признака формата воспроизводит прежние данные проверки и начальный снимок побайтово. TLS-тест начинает с реально замороженной базы API 2 и начальной политики из штатного преобразователя. Он проверяет отзыв сессии при отвязке, сохранение исходной связки в API 2 и повторное вступление с новым ключом и базовыми правами. Фикстура готовит рабочий runtime напрямую, а церемонию активации Manager проверяют отдельные сценарии.

Client получает инвентарь доступных резервных пакетов и может доказать открытие каждого из них. Сквозной тест временной комнаты получает новые live и archive пакеты от другого устройства, отклоняет старый recovery-код и проверяет обе подписи подтверждения. Готовность профиля остаётся в ожидании до серверной проверки полного актуального набора.

Manager принимает подпись владельца через `pawtalkctl migration activate --approval <file>` или использует разрешение, уже записанное Server. Он проверяет резервную копию, закреплённый образ и отпечаток переключения, фиксирует фазу активации до остановки и проверяет защищённый процесс по TLS перед записью установленного состояния. Повтор после обрыва продолжает активацию с записанным отпечатком и сохраняет исходный архив. Схема, на которой сейчас работает база, хранится отдельно от подписанных метаданных установленного образа. Проверены новый отпечаток в запущенном Server и сценарии журналирования через тестовый адаптер Manager.

Активный Server сообщает API 3 и схему 4 в подписанном `/api/config`. Подпись связывает известную идентичность сервера, начальную политику, подтверждённый cutover, экземпляр запуска и доступность голосовых маршрутов. Client владельца сохраняет доверенные отпечатки в защищённом хранилище при подтверждении миграции. При входе он сверяет их через закреплённый TLS и подписывает вызов только от обнаруженного экземпляра. Маршрут API 2 отвергается после сохранения подтверждения, включая корректно подписанный ответ прежней версии. Тест охватывает подмену подписанной конфигурации, смену экземпляра между конфигурацией и вызовом, доступ без локального основания и возврат API 2. Предоставление другим устройствам проверяемого основания для доверия к cutover остаётся открытым.

Кандидат голосового HTTP-протокола `/api/v3/voice` связывает выдачу свежего токена, heartbeat, выход и перенос с защищённой авторизацией. Client запрашивает грант через аутентифицированный API и проверяет адрес шлюза сигналинга. Выход закрывает голосовой слот и аннулирует сохранённый токен в одной SQLite-транзакции. При выходе и истечении heartbeat место остаётся занятым до подтверждения отключения LiveKit. Неудачное отключение повторяет фоновый обработчик. Новый вход всегда получает уникальный токен. Сквозной тест Client ↔ Go покрывает повтор после HTTP 503 при переносе и выходе. Нативный тест Electron ↔ LiveKit подтверждает отключение после выхода. Подключение обработчика к запуску защищённого хоста и интерфейс с сохранением локального mute/PTT остаются открытыми.

Постоянный и временный хостинг используют общий шлюз сигналинга. Для защищённой комнаты он сверяет токен с последней выдачей PawTalk, действующей сессией, подписанной политикой и голосовым местом. Изменение разрешений или вместимости очищает сохранённый хеш токена. Снятие ограничения требует нового токена. Нативные тесты подключают Electron к локальному LiveKit через тот же обработчик. Тест шлюза проверяет отклонение токена после отзыва, после возврата прав и после новой выдачи. Служебные методы LiveKit вызываются по внутреннему адресу. Остаются автоматический запрос свежего токена в Client, включение публичных маршрутов защищённого протокола и отдельная проверка уже открытых медиасеансов. Связь токена с комнатой основана на трактовке гранта LiveKit 1.13.11. [Исходный код LiveKit](https://github.com/livekit/livekit/blob/v1.13.11/pkg/service/auth.go)

Голосовые операции и шлюз на хранилище активного API 3 используют ту же сессию по подписи устройства, что и текст. Выдача гранта и сигналинг проверяют текущий экземпляр запуска и срок сессии. Проверка с тестовым HTTP-сервером за шлюзом покрывает вход слушателем, отказ после перезапуска или истечения сессии и запрет грантов комнат API 2 на шлюзе API 3. Публичное включение голоса зависит от отдельного обмена медиаключами E2EE.

Прототип голосового обмена создаёт случайный 32-байтовый секрет на период до 60 секунд и упаковывает его через HPKE отдельно для каждой допущенной голосовой сессии. Подпись устройства связывает сервер, канал, экземпляр запуска, период, подписанный снимок политики, дедлайн, хеш состава комнаты и обязательство на секрет. Client сверяет открытые ключи устройств, право Connect и отсутствие deafen с проверенной политикой. Сервер вычисляет состав по активным сессиям и актуальному допуску.

TLS-маршруты API 3 резервируют место и выдают срок подготовки на текущий состав. Публикация записывает подписанный заголовок и все пакеты в одной транзакции. Точный повтор возвращает успех. Каждый запрос чтения снова проверяет политику, состав комнаты и сессию, затем отдаёт один зашифрованный пакет. Проверка Go ↔ Client покрывает откат при сбое записи, устаревший состав, неверного автора, подмену секрета и отказ старого пакета после deafen. Main-процесс загружает ключ через закреплённый TLS.

TLS-обработчик с настроенным медиашлюзом выдаёт грант после публикации текущего ключа и проверки пакета для сессии. Подписанный грант включает ID периода и истекает не позднее медиаключа. Шлюз повторяет проверку при подключении. Выход участника атомарно аннулирует опубликованный обмен, а повторный вход с тем же составом не восстанавливает старый грант. Интеграция проверяет эту цепочку с тестовым HTTP-сервером за шлюзом.

Постоянный активный хост API 3 запускает LiveKit и голосовой обработчик сверки. TLS начинает принимать запросы после готовности медиапроцесса, выход дочернего процесса завершает хост. Тест на Windows запускает `serve` с поставляемым LiveKit и проверяет доступ к защищённому шлюзу через закреплённый сертификат. Тест режима обслуживания по-прежнему стартует при отсутствующем LiveKit. Аудиосессия Client учитывает разрешения LiveKit на передачу и приём. При запрете Speak она не открывает микрофон и отпускает его при отзыве, сохраняя локальные mute/PTT.

Запрос нового ключа за 15 секунд до дедлайна открывает следующий период. Аудиосессия может применить проверенный ключ в открытой комнате и закрывает соединение, если текущий ключ истёк. При неодновременном переходе теряются кадры, зашифрованные ключом, которого ещё нет у получателя. Нативная проверка с двумя Electron и поставляемым LiveKit подаёт тестовые ключи в аудиосессию. Она подтверждает приход RTP без декодированного звука на прежнем ключе, восстановление двустороннего звука после перехода обеих сторон и сохранение комнаты, микрофона и PTT.

Клиентский цикл поддерживает голосовое место через heartbeat и запрашивает пакеты только при изменении или приближении дедлайна. При потере сигналинга защищённая аудиосессия передаёт повторный допуск своему транспорту. Main-процесс запрашивает свежий грант для текущего ключа в существующем месте. При закрытии места сервер отвергает повторный вход. Два Electron с тестовыми ключами подтверждают автоматическую смену ключа и восстановление звука со свежим грантом после имитации обрыва сигналинга. Проверка от main-процесса до TLS API 3 использует подписанную политику владельца и отдельный тестовый медиасервер. Она проверяет ротацию после правки политики, отказ старого токена, свежий грант и отказ переподключения после выхода. Видимые участнику доказательства политики и проверка от выдачи API 3 до реального декодера остаются открытыми.

Подписанные изменения ACL канала и категории, перенос с явным выбором сохранения или синхронизации и отдельная синхронизация используют те же серверные проверки, что и внутренние транзакции политики. Client воспроизводит изменение по предыдущему снимку, включая полномочия, ранг при персональных переопределениях и границы допуска. Тест отклоняет устаревший подписанный preview, подменённое описание ACL и действительную подпись участника без нужного права. Перенос сохраняет закрытые правила, а явная синхронизация возвращает ограниченному читателю доступ с новой границы истории.

Подписанное создание задаёт начальные ACL и параметры в одной транзакции. Копия переносит определение доступного исходного канала в той же категории. Позиции истории и поколения ключей начинаются независимо. Удаление категории требует явного выбора, проверяет права на каждого удаляемого ребёнка либо закрепляет действующие ACL сохраняемых каналов. Удаление последнего канала разрешено. В подписанном снимке остаются ID удалённых каналов, а прежние записи закрыты для выдачи. Тест проверяет запрет повторного использования ID, запрет удалить скрытый дочерний канал через родителя и создание первого канала делегированным создателем пустой категории.

Подписанное изменение параметров канала требует отдельного права редактирования параметров. При новой защищённой отправке slowmode проверяется по эффективному профилю и каналу в той же транзакции, где записывается время принятого сообщения. Повтор принятой операции возвращает сохранённую позицию. Обход slowmode сохраняет технический лимит в пять новых сообщений за секунду на устройство. Тест `TestProtectedSlowmodeAcrossLinkedDevicesAndRestart` проверяет конкурентные отправки двух связанных устройств, восстановление окна после повторного открытия SQLite, границу срока и технический лимит после выдачи права обхода. Открыты интеграция публичных маршрутов и редакторов и отдельные ограничения правок и интерактивных операций.

Внутренний защищённый голосовой адаптер проверяет подписанный снимок, доступ к каналу, Connect и Speak, затем резервирует место на эффективный профиль и выдаёт короткоживущий токен в отдельной комнате LiveKit. Лимит применяется к владельцу. Уход сохраняет резерв до истечения выданного токена. Heartbeat перепроверяет Connect, передачу и приём.

Подписанная политика хранит независимые mute и deafen по каналу и эффективному профилю. Снятие deafen сохраняет mute. При изменении политики активные места помечаются на сверку в той же SQLite-транзакции. Внутренний обработчик сверяет текущий снимок и применяет `UpdateParticipant` или отключает участника. Пометка снимается после ответа LiveKit, а при сбое остаётся на повтор. Тест проверяет повтор после HTTP 503 и сохранение mute при входе со связанного устройства. С `PAWTALK_TEST_PROTECTED_MEDIA=1` Electron подключается к локальному LiveKit 1.13.11 и получает изменения разрешений в действующем соединении. Нативный тест отклоняет повтор старого токена после mute/deafen, переноса, отзыва Connect, подписанного бана и выхода. При mute LiveKit прекращает синтетическую аудиопубликацию. После отзыва Connect и бана активное соединение закрывается.

Внутренний перенос требует прав модератора в обоих каналах, доступа цели к назначению, свободного места и подтверждённого присутствия в LiveKit. Ожидающий перенос резервирует место и привязан к текущей сессии цели. Перед отключением исходного соединения сервер повторно проверяет политику и вместимость. Целевая сессия получает назначение после подтверждения отключения, а право Speak заново вычисляется при выдаче токена. `TestProtectedVoiceMove` проверяет отмену после отзыва доступа, повтор после HTTP 503, закрытое и полное назначение. Нативный тест наблюдает отключение в Electron и подтверждает подключение слушателем со свежим токеном. Открыты публичный цикл сверки и доставка переноса в приложение с сохранением локального mute/PTT, изменение вместимости действующей комнаты, голосовые ключи и приёмка аудио. Самостоятельно размещённый LiveKit не отзывает уже выданный токен при удалении участника или смене разрешений. [Документация LiveKit](https://docs.livekit.io/home/server/generating-tokens)

Client сохраняет отдельно живую и архивную головы каждого канала. Если локальная голова уже известна, продвижение требует цепочку подписанных записей с хешем каждого предшественника. Внутренний Server выдаёт до 32 доказательств за страницу с проверкой доступа к каналу, а для архива — права полной истории. В доказательствах нет пакетов ключей. Тест проверяет восстановление цепочки после пропуска поколения, отказ без промежуточного доказательства, известный откат и вторую действительную подпись на том же номере после перезапуска Client.

В [проекте ключевого протокола](013-channel-key-design.ru.md) зафиксированы предлагаемые контракты. Внутренний репозиторий SQLite хранит роли, назначения, ACL категорий и каналов, непрерывные интервалы допуска и версию в одной записи. Commit сравнивает версию, проверяет итоговое состояние и сохраняет новые интервалы одной транзакцией. Это состояние и его версия предназначены для внутренней серверной модели. Версия записи не заменяет подписанную точку политики. Публичные точки входа обслуживают состояние API 2.

Проверка `go test ./internal/access` использует реальные файлы SQLite и отдельные соединения. Она проверяет отзыв роли после повторного открытия базы, фильтрацию ожидающих событий и метаданных, конфликт двух конкурентных commit, атомарность отклонения Administrator, редактирование ACL категории, перенос с явным выбором и удаление категории с сохранением прав. Для отложенной доставки `DispatchSession` держит транзакцию `BEGIN IMMEDIATE` до окончания записи ограниченной пачки. Тест проверяет, что отмена запроса сохраняет блокировку до выхода из обработчика.

`go test -run 'TestProtected|TestAPI2Refuses'` проверяет настоящий WebSocket в тестовом HTTP-обработчике. Каждая пачка пересчитывает эффективный профиль по сессии, проверяет отозванные сессии и текущую политику. После снятия роли ожидающие метаданные и содержимое закрытого канала отсутствуют в следующей пачке. Адаптер ограничивает длительность записи кадра. Нужна проверка нагрузки с медленными клиентами и подключение к постоянной очереди событий.

Запись защищённого сообщения проверяет Ed25519-подпись устройства и сохранённое поколение ключа, затем сохраняет позицию, ciphertext и независимый receipt в одной транзакции. Подпись сообщения связывает сервер, канал, эффективный профиль, устройство, логическую операцию, ключ, nonce и хеш ciphertext. Receipt сохраняется при удалении содержимого и требует текущего доступа к исходной позиции. Тест повторного допуска использует реальные позиции, присвоенные при отправке. Текущий Server останавливает запуск API 2 при обнаружении таблицы защищённой политики. Для переключения и защиты от запуска предыдущих бинарников всё ещё нужна отдельная версия схемы.

Нативный сценарий `protected-selfhost-smoke.mjs --message-retry` теряет ответ после записи сообщения, меняет живое поколение при вступлении другого участника и повторяет ту же логическую операцию. Client использует новый ключ, nonce и шифротекст. Server возвращает исходную позицию с признаком повтора. История содержит только исходную запись, которая по-прежнему открывается у автора.

`TestProtectedArchiveClientResumesHistoryThroughServer` проверяет тот же контракт через программный Client и закреплённый TLS. Фикстура теряет ответ после записи, сравнивает ключ, nonce и шифротекст повтора со значениями первой отправки, затем проверяет исходную запись и позицию следующего нового сообщения.

Проекция v9 включает настройки в поканальное доказательство. Делегированный редактор сверяет действующую аттестацию, параметры видимого канала и доказательство `channel.edit`, а затем подписывает новые параметры и точную предыдущую ревизию. Go TLS проверяет ошибки подписи и версии, точный повтор и применение slowmode к отправке. Нативный сценарий `--scoped-channel-settings` меняет параметры текста и голоса без выдачи полной политики, проверяет потерю ответа и отсутствие изменений в остальной политике. Редактор ждёт подписанного подтверждения новых параметров перед обновлением основного окна. Интерфейс проверен в Electron отдельно на русском и английском.

`TestProtectedScopedChannelSettings` также связывает делегированное изменение голосового лимита через TLS с резервированием места на Server. Владелец получает отказ при занятом единственном месте и может занять второе после подписанного изменения лимита. Редактору параметров отказано в предпросмотре правки ACL и удаления канала. Запросы доказательств для скрытого и отсутствующего канала дают одинаковый отказ.

Редактор может подтвердить своё последнее изменение без новой подписи владельца. Client сверяет принятое изменение с исходным запросом, подписанным устройством, и проверяет полномочия по поканальному доказательству предыдущей аттестации. Server выдаёт только доказательство текущей операции этому редактору. Нативный `--scoped-channel-settings` проверяет отклонение подменённых параметров и работу со старым Server, где Client ждёт обычную аттестацию. Самостоятельная проверка новой ревизии другими Client и делегированные операции, меняющие допуск, остаются открытыми. Для них требуются доказательства эффектов перехода с соблюдением границ видимости.

Administrator с полным доступом может получить и воспроизвести подписанную цепочку политики в Client. Предпросмотр проверяет право по предыдущему подписанному состоянию, а Server заново применяет проверки конкретного действия. Нативный `--policy-administrator` проверяет обязательность восстановления, изменение параметров, создание и назначение нижестоящей роли, защиту владельца и отказ в выдаче полной цепочки после снятия права. Подписывать поканальные аттестации может действующее устройство подписи владельца.

Проекция v10 добавляет узкое доказательство для чтения и подписи изменения ролевых правил выбранного канала. Client сверяет право `channel.access.edit`, ключ устройства, источник правил и применимые разрешения с аттестацией. Персональные переопределения и правила других типов каналов в ответ не входят. Сервер проверяет подписанное изменение относительно точной предыдущей ревизии и одной транзакцией записывает политику, аудит и задачу ротации. Нативный `--scoped-channel-acl` проверяет отклонение подмены, потерю ответа и точный повтор, сохранение персонального правила, отзыв канала и смену ключа. После воспроизведения политики и аттестации владельцем редактор открывает новое поколение, а отозванный участник не получает пакет. Независимое подтверждение последствий обычными Client без новой аттестации остаётся открытым.

Делегированный редактор персональных ACL подписывает одно разрешение и его новое состояние для выбранного профиля на точной ревизии. Server выдаёт действующие правила выбранного профиля после проверки области и строгой иерархии. При записи в транзакции он сохраняет остальные применимые правила и проверяет итоговый доступ. Нативный `--scoped-personal-acl` проверяет отзыв и снятие ограничения, точный повтор после потери ответа и воспроизведение полной политики. `TestProtectedChannelACLPersonalScopeAndRetry` проверяет также отказ для скрытого, отсутствующего, равного по рангу и владельца, снятие синхронизации при изменении и постановку ротации. Полномочие редактора сверяется по v10, условия для целевого профиля проверяются серверной транзакцией и полным воспроизведением политики.

На v11 Client до подписи сверяет ранги редактора и целевого профиля с подписанной предыдущей политикой. API открывает две записи и их пути, без списка остальных профилей. Общий фиксированный вектор Go и JavaScript связывает доказательство с корнем политики. Нативный сценарий персонального ACL подменяет ранг и проверяет отсутствие POST. Сервер по-прежнему перепроверяет иерархию при записи. Независимое доказательство состава получателей после изменения остаётся открытым.

Проекция v12 также подтверждает обход ACL для обоих профилей. Нативный Windows Client проверяет доказательство для обычного участника и Administrator с меньшим рангом. Подмена или удаление признака останавливает изменение до POST. Совместимость с v10 и v11 проверена тем же набором интеграционных HTTP-сценариев.

Проекция v13 связывает группы получателей живой ротации с подписанным корнем политики. Общие векторы Go и JavaScript учитывают устройства и recovery и сохраняют корень v12. Client проверяет текущие группы при получении поканальной задачи и останавливается до публикации пакетов при подмене доказательства. Контрактный тест восстанавливает состав оставшихся получателей по предыдущему корню и закрытому отпечатку удалённой группы.

При одиночном делегированном запрете `channel.view` поканальная задача содержит подписанное намерение, закрытое доказательство права редактора, оба доказательства ранга и открытия по предыдущему составу получателей. Client проверяет полномочия и вычисляет точный состав оставшихся по предыдущей аттестации. Подпись поколения связывает этот переход с задачей и отпечатком пакетов. При открытии адресат независимо проверяет намерение, предыдущий допуск издателя и своего устройства и подпись поколения. Сервер передаёт ему только эти доказательства допуска и поканальное доказательство перехода.

Нативный Windows selfhost проверен и с новой аттестацией, и при её отсутствии. Оставшийся участник без права редактирования отклоняет подмену подписи и отпечатка исключённой группы, один раз публикует ключ при потерянном ответе и открывает подписанное поколение. Другой оставшийся участник открывает тот же ключ по собственному поканальному доказательству, исключённое устройство получает отказ. До аттестации новой ревизии участник с правом отправки пишет под новым ключом, а читатель открывает старое и новое сообщение в одной ленте. Отсутствие или подмена доказательства автора блокирует чтение нового сообщения. Для автора проверяются право `message.send` по предыдущей политике и сохранение допуска. Статус чата и отправка учитывают подтверждённое право, исторические ключи сверяются с цепочкой подписей до подтверждённого поколения. Правки и другие переходы политики для этого пути остаются открытыми.

Проекция v14 подписывает отдельный корень архивных групп. Общие векторы Go и JavaScript сохраняют корни v12 и v13 и сверяют v14. Поканальная архивная задача открывает только состав получателей с полной историей. В нативном Windows selfhost обычный участник отклоняет подмену архивной соли, публикует точный состав и открывает через архивные ссылки сообщение до своего вступления. Оставшийся читатель с ограниченной историей читает живые сообщения и получает отказ в архивной задаче и пакете. Предыдущее архивное доказательство позволяет подтвердить исключение профиля с полной историей после одиночного персонального запрета.

В нативном сценарии исключения целевой участник сначала подтверждает доступ к архивному пакету. Владелец подписывает одиночный персональный запрет через поканальный маршрут и аттестует следующую ревизию. Оставшийся обычный участник отклоняет подмену отпечатка удалённой группы и публикует ключ один раз после успешного повтора. Исключённый участник и оставшийся читатель с ограниченной историей новый архивный пакет открыть не могут.

В отдельных нативных сценариях без владельца Client проверяет аттестованную предыдущую политику и одиночный персональный запрет. Оставшийся обычный читатель публикует живое и затем архивное поколение до аттестации новой ревизии. Подпись архивного поколения связывает отпечаток перехода и ключ обёртки. Исполнитель проверяет предыдущий архив и связывает текущую пачку с подтверждённым живым поколением того же перехода. Другой обычный читатель отклоняет удаление или подмену отпечатка и открывает прежний текст по ссылкам нового архива до аттестации владельцем. Исключённый участник и читатель с ограниченной историей архив открыть не могут. Если у цели раньше был только живой доступ, поканальная задача подтверждает точный неизменный состав получателей по предыдущему архивному корню. Независимый читатель открывает старый шифротекст по этому доказательству до аттестации владельца. Правки и другие изменения доступа ещё открыты. Отдельный нативный Windows-сценарий восстанавливает обычного участника с полной историей на новом устройстве до запрета. Архивная ротация использует ранее адресованный recovery-пакет для старого архива и адресный пакет устройства для нового живого поколения. Удаление доказательства прежнего допуска recovery останавливает публикацию. Повтор с подлинным доказательством публикует ключ один раз, другой обычный читатель открывает старую историю до новой аттестации.

Для неполной архивной пачки Client проверяет, что последний живой источник входит в цепочку до закреплённого живого поколения. Следующие пачки, страницы доказательств и обратные ссылки архива используют поканальное доказательство издателя промежуточных архивных поколений при совпадении подписанного перехода и текущей политики. Интеграционный Go-тест публикует две пачки на 129 синтетических живых поколениях и проверяет старые ссылки и доказательства издателей, включая отказ после смены головы. Нативные Windows-сценарии покрывают одну пачку нового архива.

Проекция v15 закрепляет группы получателей правки с ограниченной историей по эффективному профилю и позиции оригинала. Поканальное основание открывает только группы точного пересечения допуска. Плоские доказательства прежних ревизий сохраняются. Общие векторы Go и JavaScript сохраняют корни v12–v14 и сверяют v15. Нативный Windows selfhost отклоняет подмену профиля и соли позиции до PUT. Правку с подлинным доказательством открывает читатель, допущенный до оригинала. Более поздний читатель видит содержимое только в пределах своего допуска. Контрактный тест подтверждает удаление профиля без раскрытия его устройств.

Точный переход персонального запрета v15 позволяет публиковать поканальную правку до новой аттестации. Автор проверяет прежнее право отправки, состав получателей на позиции оригинала с закрытым отпечатком исключённой группы при её наличии и ключ обёртки, подписанный подтверждённым издателем архива. Архив должен покрывать проверенное живое поколение того же перехода. Чтение сохранённой правки восстанавливает компактное доказательство из неизменяемой политики подписанного поколения и отдельно проверяет текущий допуск читателя. Если изменение настроек продвигает политику без смены поколений, соответствующие адресные пакеты подтверждают прежнего подписанта и сохранённый текущий допуск.

Проекция v16 доказывает точный эффект одиночного поканального запрета просмотра по именованной роли при живой ротации с новой аттестацией. Общий вектор Go и JavaScript учитывает персональные исключения, разрешения других ролей и обход ACL администратором. В Windows selfhost обычный редактор сохранил допуск по персональному разрешению и выполнил ротацию. Исключённый участник с той же ролью не получил новый ключ. Подмена списка исключений или доказательства состава получателей блокировала публикацию. Без новой аттестации обычный редактор также опубликовал подписанное живое поколение после восстановления корня прежних получателей. Независимый читатель с ограниченной историей открыл адресный ключ и проверил подпись автора нового сообщения по предшественнику. Исключённый профиль не получил живой ключ и потерял доступ к каналу.

В Windows selfhost также проверена архивная ротация после этого запрета до новой аттестации. Подмена закрытого отпечатка исключённой группы блокирует публикацию. Независимый обычный читатель открывает текст до своего вступления через новую архивную связь. Читатель с ограниченной историей видит только недавний текст, а исключённый профиль с прежним полным доступом не получает ни один из текущих ключей.

Проверен сценарий HIST-06 без новой аттестации. Автор с ограниченной историей правит сообщение, отправленное до запрета по роли. Оставшийся ограниченный читатель и независимый архивный читатель открывают правку. Исключённый читатель оригинала и позднее допущенный участник её не открывают. Подмена закрытого отпечатка исключённой группы или доказательства позиции оригинала останавливает PUT. Go-фикстура сохраняет правку, продвигает политику до следующей аттестации и подтверждает выдачу старой редакции по неизменяемому архивному поколению.

`TestProtectedArchiveFullHistoryInvitationWorkBound` запускается с `PAWTALK_TEST_ARCHIVE_SCALE=1`. На 10 000 подписанных архивных поколений приглашение прочитало один старый пакет ключа (80 байт), перепаковало один старый ключ (60 байт) и не читало архивные связи. При вступлении получатель не обходил цепочку. Чтение самого старого сообщения потребовало 10 001 запрос связи и 33 018 672 байта сетевых ответов. Один локальный прогон измерил 223 мс на приглашение и 54,7 с на историческое чтение. Тестовая обвязка отключает ограничение частоты только для исторических запросов связей. Для них по-прежнему действуют TLS, рабочий обработчик и проверка допуска.

С `PAWTALK_TEST_ARCHIVE_RESUME=1` тот же тест повреждает ответ №2048. Client прерывает выдачу страницы и при следующем вызове начинает с того же звена после проверки текущей политики, пакета получателя и головы архива. Повтор открывает сообщения поколений 1, 2500 и 5000 за 7954 запроса. Новый Client открывает все три сообщения общим проходом за 10 001 запрос. Замеры JS-кучи после сборки мусора во время чистого прохода оставались в пределах 10 964–11 416 КиБ. Контрольная точка одноразовая, хранится в главном процессе до двух минут и сбрасывается при выходе, отзыве видимости или несовпадении входных доказательств. После перезапуска приложения чтение начинается с головы.

Сводка очереди в боковой панели защищённого сервера показывает ожидающие и выполняемые задачи для доступных каналов. Успешно прочитанная пустая очередь отображается как ноль. При потере связи или отсутствии данных состояние неизвестно. Допуск к отправке определяется проверкой политики и ключа. Go проверяет выборку под той же блокировкой, что и видимые каналы. Синтетический Electron-тест проверяет обычного участника, переподключение и сохранение черновика на русском и английском.

Для текстового канала Server выдаёт рабочее окно смены живого ключа с текущей ревизией политики. Client сверяет её с проверенной политикой и самостоятельно открывает и проверяет пакет устройства. Только совпавшие доказательства дают зелёный статус. Действующий grace и ожидаемая подготовка показываются жёлтым. Красный приостанавливает отправку и сохраняет черновик, а подтверждённая ошибка остаётся видимой без связи. Нативный `--text-protection-status` проверяет подготовку, успешное открытие ключа, подмену подписи, отключение сети, повторную проверку и доступную отправку в grace после исключения другого участника.

Для KEY-11 пользователь может явно отложить отправку текста до проверки пригодного ключа. Client хранит намерение вместе с черновиком в текущем сеансе приложения и повторяет тот же идентификатор операции. Server проверяет непрерывность допуска по сохранённым снимкам политики в транзакции записи. Новый допуск прекращает автоповтор и сохраняет текст, даже если начальная позиция истории совпадает. Нативный прогон дожидается реального истечения grace и проверяет одну квитанцию после смены ключа. Electron проверяет сценарий компоновщика на русском и английском.

Голосовой индикатор привязан к конкретному серверу и каналу. Client проверяет подписанный голосовой ключ, состояние E2EE комнаты и шифрование локальной пробы ожидаемым ключом в LiveKit worker. При подготовке ключа, смене ключа или потере подтверждения управления Client приостанавливает микрофон и воспроизведение. Нативный `--voice-protection-status` подтверждает, что при подключении и смене подписанного состава статус остаётся жёлтым до ответа настоящего worker. Тест подменяет тег аутентификации в ответе по закреплённому TLS и передаёт типизированный отказ проверки в голосовую сессию. Красный статус сохраняется после отключения. Отдельная проверка окна на русском и английском покрывает все состояния, доступность управления подсказкой и изоляцию каналов.

Ротация подписывает хеш снимка политики, номер его версии, хеш предыдущей записи поколения, ID задачи и lease, ID ключа и хеш пакетов. Смена состава читателей ставит задачу в SQLite в транзакции политики. Инициатор имеет приоритет в первые пять секунд. После истечения 15-секундного lease другой подходящий участник может взять ту же задачу. Подпись с прежним lease отклоняется. При сохранении сервер сверяет точный набор живых и архивных пакетов с зарегистрированными получателями из снимка, затем атомарно сохраняет поколение, пакеты и закрывает задачу.

Тесты покрывают сохранение очереди после открытия БД, замену исполнителя, конкурентные ротации, просроченный снимок, подмену пакетов и исходный дедлайн grace. Адресные пакеты поколения зашифрованы HPKE и связаны с подписанным корнем дерева пакетов. Получатель получает один пакет и доказательство включения. Тест Go ↔ Client проверяет реальные шифротексты, чужой ключ, подмену пакета и отзыв доступа после выдачи.

Живая и архивная ротации используют отдельные задачи, lease и порядковые номера. Читатель с ограниченной историей может обновить живой ключ и отправлять сообщения, пока архивная задача ещё ожидает завершения. Архивный исполнитель должен иметь полную историю и предыдущий архивный пакет. Подписанное архивное поколение включает непрерывный диапазон живых поколений и ссылку на предыдущий архив. Lease фиксирует диапазон до 128 новых живых ссылок. Если живой ключ успел смениться, оставшийся диапазон остаётся в очереди. По этому lease исполнитель может загрузить только свои исходные пакеты из указанного диапазона, включая предыдущие живые поколения.

Интеграционный тест `TestProtectedArchiveClientResumesHistoryThroughServer` проводит живые и архивные ротации через HTTP-фикстуру Go Server и основной процесс Client. Client вычисляет текущих получателей по проверенной политике и проверяет подписанта по версии, с которой связано поколение. Для доступа к прежним поколениям после перезапуска он воспроизводит политику от закреплённой начальной подписи до сохранённой контрольной точки. Тест отклоняет подменённый ключ получателя, добавление ограниченного читателя в архивную задачу, архивное поколение с подписью этого читателя в версии без нужного права, конфликт головы политики, подменённое звено, подменённый ключ в запросе и недействительный lease. Тест через закреплённый TLS охватывает четыре live-поколения и три архивных. Читатель сохраняет историю непрерывного допуска после снятия полной истории. После повторного ограниченного допуска он видит только новый интервал, а после выдачи полной истории открывает старые сообщения через архив. Отдельный читатель в той же фикстуре открывает старые сообщения через архив с узкими доказательствами. Тест отклоняет отсутствие доказательства архивного подписанта и проверяет, что читатель не запрашивает полную цепочку политики. Замеры длинных цепочек остаются открытыми.

Владелец подписывает начальный снимок до первой ротации. Затем подпись указывает предыдущую запись, тип и ID операции, нормализованное изменение и хеш результата. Реализованы изменения ролей и регистрация/отзыв собственного ключа устройства. Транзакция сохраняет доказательство, новый снимок и задачи для затронутых каналов. После закрепления начального снимка прежние неподписанные мутации блокируются. Новая регистрация требует канонического X25519-ключа. Сервер связывает разрешение на отправку с текущим ключом устройства и выданным ему пакетом поколения. Старый ключ и его неканонический эквивалент повторно зарегистрировать нельзя.

Адаптер сверяет подписанную голову с применённым снимком и её непосредственным предшественником. Проверяющий в основном процессе Client проверяет страницы подписей от закреплённой начальной записи, совпадение хеша итогового снимка и сохраняет точку через защищённое хранилище. Откат ниже известной версии, другой хеш на той же версии, разрыв цепочки и недоступное хранилище блокируют принятие страницы. Идентификатор доказательства вычисляется от подписи и не зависит от форматирования JSON. Тест `TestProtectedPolicyProofsVerifyInClient` использует страницы Go Server, реальные Ed25519-подписи и тестовое хранилище для проверки повторного чтения точки.

Client воспроизводит поддерживаемые изменения по предыдущему проверенному снимку. Для ролей проверяются ранги, делегирование прав, действующие ACL и требование восстановления перед выдачей Administrator. Для ключей допустимы только изменения собственной регистрации и её отзыва. Итоговый снимок должен соответствовать подписанной операции. Сохранённая контрольная точка включает снимок для продолжения проверки после перезапуска, а страницы ограничены 32 доказательствами и 8 МиБ до кодирования. Для нового допуска позицию выбирает Server при commit. Client проверяет сохранение прежних непрерывных интервалов. Интеграционный тест отклоняет правильно подписанную операцию от участника без прав и подписанный владельцем снимок с изменением recovery вне операции.

Начальная подпись политики фиксирует состав устройств-подписантов и их эффективные профили. Client закрепляет профиль владельца, ID его устройства и хеш начального доказательства, затем проверяет подписантов по предыдущему проверенному снимку. Для регистрации необходимы подписи действующего устройства эффективного профиля и нового устройства. Обе подписи связывают операцию с сервером, эффективным профилем, версией и итогом политики. Отзыв устройством того же эффективного профиля выводит ID подписанта из обращения, удаляет его из получателей шифрования и ставит задачи ротации в одной транзакции. Действующая сессия сразу теряет защищённый доступ. Тест Go и Client проверяет незарегистрированное устройство, корректную регистрацию, повтор согласия для другой операции, отзыв и отклонение последующей подписи от отозванного устройства.

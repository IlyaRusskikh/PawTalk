# Channel key design and verification gates

Status: design candidate. The synthetic probes cover the archive key graph and edit recipients with in-memory keys. API 2 has no channel key packages or signed policy chain.

## Authority and checkpoints

The trust anchor must bind the server ID and policy genesis to the initial owner’s public identity. Admission must verify an invitation signed by an authorized issuer under that anchor. Bind its deadline, use limit and a separate invitation verification key to the signature. The link privately carries the corresponding redemption signing secret; it never reaches the server. A redeemer signs the server and invitation IDs, redemption ID, profile and exact device certificate with this secret and proves possession of the device keys separately. The verifier checks expiry, redemption counts and uniqueness against the previous policy state. Anyone with the link can redeem within its admitted limits. The authenticated redemption, current policy and recovery readiness determine which public identities may receive keys. Pin the server TLS identity before sending credentials.

Encode signed fields with PawTalk length-prefixed frames and versioned domains. Include the server ID, previous policy digest, sequence, logical operation ID, actor profile/device, grant basis and normalized mutation. Verify actor authority against the previous signed policy and proposed outcome. Each device certificate binds the effective profile, signing and encryption public keys, and its authorization version. A signed rotation binds the channel, policy digest, expected previous epoch, task ID, epoch and intended devices or recovery recipients, purposes and package digests. Derive the expected recipients from verified policy. A lease authorizes attempting work on that task; the result still requires policy verification and a compare-and-swap against the task's basis.

Persist a verified policy checkpoint and relevant channel heads in protected Electron storage before marking them usable. A known older checkpoint and a different digest at the same sequence fail closed. An advancing checkpoint needs a verified consistency path to the stored head. Without an independent newer witness, a client cannot distinguish an unseen policy update from a server withholding it. This affects restore and offline status, even with correct signatures. G4 requires protocol and integration tests for proofs, substitution and competing heads.

After verifying the full chain, the pinned owner device can sign a detached `pawtalk-policy-scope-attestation-v1` for the root. It binds the server, original checkpoint, revision and digests to the versioned channel root. API 3 sends only those claims, the signature and the device public key. A participant checks the key against the pinned ID, persists the checkpoint and verifies their own admission, including first position and full-history eligibility. The Client rejects known rollback and a competing record at the same revision.

When requested, API 3 attaches signer evidence to a delivered key epoch and author evidence to an accessible live message. It derives that evidence from the signed epoch policy and the individual device path for the visible channel. The accessible record determines which signer is disclosed. With verified admission to the current continuous interval, Client opens addressed live packages and reads and sends text without downloading the complete policy snapshot. A full-history reader can also follow signed archive links with scoped signer evidence. After the walk, Client rechecks current full-history admission. For imported text, Client binds the verified archive genesis to the migration link and verifies the owner's migration signatures. Autonomous validation of delegated policy authority remains open.

The v6 channel leaf also commits separately to the live and archive rotation recipient lists. Each list uses a separate salt derived for that channel, purpose and policy revision. The active executor receives the salt only for its assigned purpose. It recomputes the complete recipient commitment and checks its own device proof before sealing packages. An archive executor additionally verifies each source package’s historical signer, the preceding archive signature and contiguous live coverage. The background worker can take over an eligible task using an owner-attested root already published to the server.

On reconnect, the pinned owner device receives up to four revisions awaiting attestation. It verifies them in one pass from the anchor to its locally verified checkpoint, publishes the current revision first, and fills the gaps. TLS tests cover two missed attestations, rejection of an altered historical snapshot and denial of the pending list to an ordinary participant. Delegated changes still need evidence of authority and recipient effects scoped to visible channels.

For a change signed by the pinned owner device, the Client submits the policy signature and scoped root attestation in one request. The Server stores both proofs with the new policy, rotation tasks and audit entry. An exact retry returns the existing proof. The TLS test rejects an invalid attestation without advancing the revision, then simulates loss of the commit response. An ordinary member retrieves the attestation immediately after commit, and the retry returns the same digest without reapplying the change.

During migration preparation the Client also signs the initial root attestation. `migration-stage-policy` stores it with the initial policy. The integration test rejects a damaged attestation before persisting the policy, retries staging with the same digest, and checks that an ordinary member can retrieve the first revision's attestation after cutover.

The v8 voice leaf commits to a tree of eligible devices with separate salts. Each entry binds the effective profile, public agreement key and signing key. The tree includes active devices with Connect and excludes deafened members. Runtime operations still enforce mute, Speak and timeouts. The Server loads the roster for a voice epoch and its proofs in one transaction. The main process verifies the current attested root, channel, roster digest, each device and the package author's signature. Signed policy establishes eligibility. The Server reports which sessions are present. Text leaves retain the v7 format, and stored v3–v7 proofs remain verifiable.

The v7 policy leaf binds the channel type, category and a tree of devices with the effective `channel.edit` grant. Signing devices qualify independently of agreement-key enrollment. The server discloses only the requesting device’s entry for an authorized channel. The delegated reorder preview verifies the source and anchor against one attested root, checks their ordering group and compares the returned operation with the request. TLS tests cover a text and voice channel in the same category, denial after grant removal and substitution of the category or anchor. Saving the signed reorder is supported. Autonomous verification of its result by other clients remains open.

The v10 leaf binds the channel type and category, order editor root, v9 settings digest and ACL proof root. The ACL root combines two commitments. The first binds the synchronization flag, the SHA-256 digest of canonical JSON for applicable role rules and a channel-specific HMAC salt. The second commits to a tree of devices with the effective `channel.access.edit` grant using separate HMAC derivations for salt and order. Server checks the current grant within a transaction and discloses the applicable role rules and the requesting device's proof. Personal overrides remain in the full policy. Client checks the scoped proof against the signed attestation.

The delegated edit signature binds the server, the cutover boundary, profile and device, operation, exact predecessor and the digests of the old and new role rules. Server carries forward effective personal rules within the transaction. Full policy replay checks the signature, authority, permitted transition and admission boundaries. Scoped key recipients use the new attestation to verify key eligibility. Verification of all transition effects within a narrow scope without a new attestation remains open.

For a personal edit, the device signs the target profile ID, one permission and an `allow`, `deny` or `inherit` rule along with the channel and exact predecessor. The editor's grant is verified with v10 evidence. A separate scoped request returns only the selected profile's rules. Visibility, rank and effects are checked during application and full replay. The atomic change localizes the effective ACL by channel type and replaces only the signed permission.

Projection v11 adds a `@pawtalk-profile-ranks` leaf to the policy tree. It commits to a compressed binary trie of active effective profile ranks. A revision- and profile-specific HMAC salt blinds both the position and commitment from the public profile ID. A statement binds the ID, rank and salt. A critical action opens proofs for the actor and selected target. Client checks the attestation, both paths and the strict hierarchy before signing. Other profiles remain private. This proof belongs to the preceding policy. Projection v12 binds channel ACL bypass to the same rank leaf. Ownership and the base `server.administrator` grant are evaluated independently of rank. Effects on admission are verified separately.

API 3 saves a reorder as a separate signed operation. The device signs the source, anchor, direction, operation ID, policy head and digest of its editable sequence. The second wire version uses an HMAC under the private policy seed and binds the digest to the actor and source channel. This keeps a proof recipient from testing guesses about hidden channels against a public hash. Legacy receipts remain available for operation retries. Server verifies the signature, both permissions and the sequence in one transaction. The layout, receipt and audit entry are stored together. The visible channel list uses the saved layout while hidden and read-only channels keep their slots. A reorder uses the current signed policy and leaves its revision in place. A delegated participant previews and applies a reorder in the application window. The anchor picker lists editable channels in the applicable group and the dialog closes on revocation. The audit log verifies an individual reorder by its signature digest. The Client checks the author’s signature and both historical `channel.edit` proofs. Evidence requires current visibility of both channels and unchanged ordering groups. Full verification of the published order remains open. A move relative to a hidden anchor can change the relative order of two visible channels. The Client needs to verify the result while keeping that anchor private.

Two delegated edits can carry valid signatures over the same preceding policy. When a live epoch is accepted without a successor attestation, its signature must bind the exact authorized channel transition as well as the task, previous generation and package digest. Otherwise a proof for one valid edit could be paired with an epoch created for the other. A verified channel transition authorizes that channel's live epoch and leaves global policy verification with its own checkpoint.

Live messages in that epoch carry a scoped predecessor proof for the specific author's device. The reader verifies `message.send`, the retained author's identity and the signature with the proved key. The local transition authorizes the surviving writer's chat status and sending until a later policy requires separate proof. Earlier addressed live packages retain the verified admission boundary and must link to the pinned generation through signed epoch records.

Projection v15 adds a second position commitment for limited edit recipients. All devices of an effective profile share its continuous-admission start. Each profile leaf binds the complete group with independent inner and outer salts. The position opening binds the exact eligible group set. An authorized edit basis opens only the groups that can read the original position. A predecessor set can be reconstructed with an opaque excluded leaf and the surviving openings, which keeps the inner salt and excluded device records private. Under a verified single personal denial, a retained author can use this proof to seal a scoped edit without the successor attestation. The public wrapping key belongs to the verified archive epoch of the same live transition. The reader verifies the original author and that archive signer against the historical proof and checks its own current admission independently.

## Channel secret graph

The selective disclosure prototype derives a per-text-channel recipient projection from the same policy. Each projection commits to public package keys, device signing keys and archive eligibility. It derives access using the existing View and Full History checks. Other readers' admission positions and ACL rules are outside the proof payload.

The tree always has 1024 positions to conceal the total channel count. Independent HMAC outputs from a private random seed rank real and padding leaves. A leaf binds the channel ID digest, a distinct salt and the projection digest. The recipient learns only the disclosed leaf's salt, position and ten sibling hashes. Go produces the path. A Client with the full policy recomputes the root and verifies the path. The interoperability test changes the channel, archive eligibility, salt and position.

The `pawtalk-protected-policy-v2` signature domain binds the root to the server, author, and revision. A new migration creates the initial blinding seed in the transaction that enrolls the owner's device key. Retrying preparation uses the stored seed. A policy preview generates a fresh seed for full verification. The owner Client first replays the transition and recomputes the root, then signs. The server recomputes the root at commit and during startup chain verification. Previously signed revisions without a root remain readable. Once a root is present, later revisions must carry one.

Inclusion alone does not establish the policy author's authority. Independent projection verification depends on transition verification against the previous state, including delegated authors. The blinding seed stays in the owner's full proof.

In `pawtalk-protected-policy-v3`, the channel leaf carries the root of a separate recipient tree. Each statement binds the effective profile, device, signing and encryption keys, archive eligibility and first position of continuous admission. Separate HMACs derive the salt and ordering for each channel and recipient. The API returns the requesting device's statement, its salt, path and the visible channel's recipient count. Other statements and the revision seed stay private. Client checks the statement against its verified root before opening an addressed package. Projection v13 adds a sorted commitment to live recipient groups per effective profile. Each group uses independent HMAC salts for the profile leaf and the opaque digest of its device and recovery entries. A verifier can reconstruct an attested previous root from the surviving groups and one opaque removed leaf. The opening of that leaf contains its outer salt and digest. The inner salt and the removed device entries stay private. The normal scoped live rotation now verifies its full group opening. For a single delegated personal `channel.view` denial, the live epoch can be published and its addressed key opened using the predecessor and the signed transition when a successor attestation is unavailable. The reader sees the prior admissions of its own device and the signer. Other live transitions use the attestation path. Projection v14 binds the archive recipient groups with independent purpose-specific salts and hash domains. The scoped archive claim opens only the exact archive audience. For a single scoped denial of a profile with full history, a separate previous archive opening proves the precise removal without disclosing its earlier devices. The archive epoch signature includes the archive-purpose transition digest and wrapping key. Without a successor attestation the executor verifies the predecessor archive and a source batch that reaches the signed live head for the same denial. The reader opens an addressed archive head using the prior full-history admissions of its own device and the signer, walks linked epochs, and rechecks the exact current head before releasing plaintext. For partial batches the executor verifies the last live source against the pinned live chain. Later archive batches under the same transition carry scoped evidence for the intermediate archive signers. For a denied live-only profile the unchanged archived roster opens against the same predecessor archive root. An old source may use a recovery-addressed packet when the recovery identity and full-history admission are unchanged across the verified deny. The executor verifies its recovery admission against the predecessor and verifies the old source signature against the attested policy of that source. The new live source still uses the current device package. Older v2 revisions remain verifiable. Verification rejects a downgrade from a known newer projection. Delivery of an older live package within the continuous admission includes a device proof for the epoch policy revision. Client checks it against the verified historical root and then rechecks current admission. A single proof suffices when both revisions match. A new migration pins v9 when the owner device enrolls. Previously staged migrations keep their original format and commitment. Updated Client offers v17 for signed changes to active policy.

Projection v16 adds a counted Merkle root for the exact visibility losses caused by a single named-role `channel.view` denial. The selected leaf binds the role, previous and next canonical ACL digests, and the list of newly denied effective profiles. An Allow from another named role, a personal Allow, or an administrator bypass preserves visibility. The scoped live rotation verifies the predecessor attestation, the editor signature, and the effect proof. It rebuilds the previous attested live root from current recipient groups and opaque leaves for the excluded groups. An excluded profile can lack a leaf if it had no eligible device or recovery key. The signed live epoch carries a role-specific transition digest. A scoped reader without a successor attestation verifies the effect, its own previous admission and the prior admission of the epoch signer. The reader verifies each message author from the same predecessor and checks its continuous admission. The underlying ACL rules and excluded device records stay private. An archive lease uses the same role effect with the independently salted archive groups. The executor checks that the source batch reaches the verified live chain for that role transition. Each archive epoch signs a purpose-specific transition digest and its public wrapping key. A scoped reader verifies the addressed package, current head and linked archive epochs before returning history. Recovery-addressed sources require unchanged full-history admission and recovery identity. For a scoped edit after the role denial, the writer rebuilds the predecessor commitment at the original message position using surviving limited groups and opaque leaves for excluded groups that were eligible at that position. The writer verifies that the signed archive wrapping key covers the marked live head for the same transition. Stored edits reopen the immutable archive policy for the author and wrapping signer, and the reader verifies its current admission independently.

API 3 over TLS discloses the path to the current leaf for a visible text channel. The response carries the requested channel ID, policy revision and digest, individual leaf salt and sibling hashes. The recipient roster, ACLs and other channel positions stay in the full proof. The server caches only the current revision's tree and rechecks visibility in the delivery transaction. The same path accompanies the requesting device's key package. A Client with a verified full chain derives the expected leaf and refuses to open a package if the proof is missing or invalid for a revision that commits to a channel root. A Client without the full chain still needs an independent basis for trusting that root.

At startup the Server replays the full chain with the same authorization rules as a policy commit. The previous revision must authorize the resource change. The full result and channel root must match. Signed snapshots omit current message counters. A new admission uses its signed position and a continuous admission retains its original position. In a single transition, new admissions to an existing channel share a position at or above the previously witnessed floor. The Client saves that floor in its local checkpoint. This check cannot reconstruct a live counter from missing records. Full-chain verification is the basis for the selective proof format. Participant-visible proof of a delegated author's authority remains open.

Recipient packages use HPKE base mode with X25519, HKDF-SHA256 and AES-128-GCM as specified in [RFC 9180](https://www.rfc-editor.org/rfc/rfc9180.html). Each package has a 32-byte encapsulation and 48 bytes of ciphertext and tag. Its context binds the server, channel, policy basis, epoch, task and lease, recipient, public key and purpose. The Ed25519-signed epoch record carries the root of the sorted package tree. The client opens a package only with a valid inclusion proof. The proof reveals tree size and leaf position while hiding other recipient identities. The internal server adapter delivers the device's own package for the current epoch after checking current access. The verified chain supplies trust in the signer and policy basis.

For each text channel epoch generate independent live and archive secrets. The full-history head opens that epoch's live key and a backlink to the previous archive secret. Give full-history devices the latest head. A limited-history device receives only eligible live keys for its current continuous admit interval. Key packages never move backwards from the live graph into the archive graph. Rotate at a new limited-history boundary before giving the new reader a live key. On a full-history downgrade, keep the profile's original continuous admission boundary and rotate secrets whose distribution narrowed.

Use separate contexts for live text, files, edit wraps and archive links. An edit uses a fresh content key. Wrap it for the verified currently eligible limited readers of the original message, and for the current archive head used by full-history readers. Future full-history readers can find that wrapper via the archive chain. The edit context binds the message ID, original position, revision, edit epoch, author and device. Each revision needs an author signature over context and authenticated envelope commitments. Derived objects and reference metadata must follow original access at the HTTP and subscription boundaries.

The `pawtalk-protected-epoch-v2` archive format signs a public X25519 key for revision envelopes. HKDF-SHA256 derives the private key from the archive epoch secret in a separate context bound to the server, channel, generation and secret ID. A history-limited writer can form an HPKE envelope using the verified public key without receiving the archive secret. A Client opening an addressed archive package checks that the received secret derives the recorded public key. V1 records remain verifiable. Opening the persistent Server queues a normal rotation for a legacy archive head and preserves its signature and links. The Server and Client checkpoints reject a return to v1 after accepting v2.

The revision prototype generates a random 32-byte text key, one HPKE package for the archive head and one HPKE package per limited recipient in the verified list. The Ed25519 signature binds scope, original position and original digest, revision number and previous digest, operation, author and device, policy, archive head, ciphertext, archive envelope and the root of the addressed packages. The test checks substitution rejection, opening through the archive chain and isolation from an old archive secret and unrelated device keys.

API 3 prepares and accepts a revision only for the author with original access and Send permission. Pending archive rotation blocks preparation and publication. The transaction rechecks policy, the archive head, prior revision, exact limited recipient set and signature, and stores the revision, packages, receipt and audit entry. A limited-history reader gets only their own package with an inclusion proof. A full-history reader opens the revision through the archive. Every delivery rechecks access at the original position. Deleting the original removes its revisions from active delivery.

The main process verifies the original's signature and digest, author authority at the publication revision and exact recipients against locally verified policy. Before encryption it compares the archive epoch's recipients with the current archive audience. Revisions appear at the original position and preserve the send time. The open timeline receives scoped changes through an opaque cursor, rechecks access and updates loaded messages in place. Retrying from the open window reuses the saved encrypted attempt. Publication stops when the audience is unverified. A v4 channel proof binds the author’s Send grant and the archive audience digest to the signed root. A reader compares the archive audience at the policy revisions of the edit and the archive epoch. TLS tests open a limited-history package and a full-history archive envelope, reject a substituted author grant and confirm that readers never request the full snapshot. The v5 policy also commits the exact limited-history audience at each original position. The publish proof opens only that audience’s keys and salt, with sibling digests for other positions. A scoped author verifies the complete list and the archive address before encrypting. The Server rechecks the same inputs when committing. Older policy versions and reassigned authors of imported originals may still require the full chain.

A limited rotation executor can prepare live material without an archive secret. Linking an archive head requires a remaining verified archive custodian with the earlier head or a separately proven bridge design. Persist pending archive work when no qualifying custodian is available. Bounded batches and verified checkpoints are needed for deep traversal. Retention of an archive link depends on reachability of retained content, not the age of the audit record.

## Revocations and retry

Persist the first deadline for each revoked generation at the policy commit. Restrict old generations to the current and immediately preceding generation with their original deadlines. Check current membership and access independently at mutation and delivery. The official client prefers the new key as soon as it is available. A prior live key during grace can still decrypt any ciphertext written under it. Edits to prior objects require a verified recipient set and a safe archive destination before publication. In a batch that revokes some readers and admits new limited readers, never send the previous live key to the newcomers. Delivery of messages accepted during that transition requires separate eligible key packages or later eligible rewrapping. This case needs an integration test before enabling grace with mixed batches.

Use one stable logical operation ID and a separate cryptographic attempt ID for each fresh envelope. Commit the message and logical receipt in the same transaction. Query the logical receipt after an ambiguous response; a later authorized attempt returns the existing result if one was already committed. Bind the immutable actor, channel, operation kind and object to the logical ID. Authenticate and authorize receipt reads and protect its result from becoming a channel metadata leak. G3 still requires races between accepted, lost, stale and re-encrypted attempts.

## Recovery, migration and voice

Recovery uses independent signing and recipient material derived with domain separation from a locally generated high-entropy secret. Register only the public recovery identity; decrypting a packet does not prove authority. Recovery signs the current challenge, policy identity, action and new device keys. Verify against the current published recovery identity and membership, revoke the old sessions/devices as applicable, and commit resulting rotation tasks atomically. G5 requires ban, downgrade, replay and old-package tests.

Runtime enrollment derives the public keys from the same code format as migration. A 60-second challenge binds the server, cutover, effective profile, device and policy head. Client signs the intent with the recovery identity and the active device. Server checks possession of the separate X25519 key using an HMAC from ECDH. Policy proofs contain public evidence and an ordinary member receives a narrow receipt. Replacement targets new epochs at the new recovery recipient and retires the old keys. Readiness requires separate confirmation that the current key packages can be opened.

A new live or archive recovery package carries the epoch secret and a separate random 32-byte opening-signature seed inside HPKE. The corresponding public key and ciphertext share a leaf in the signed epoch tree. The package is 144 bytes. Device packages and previous 80-byte records retain their exact format. On startup the Server schedules updates for eligible older runtime packages and preserves the signed epochs and leases.

API 3 lists packages for the current recovery identity in accessible channels and delivers them individually. Archive requires full history. For limited live history the Client checks continuity of admission in current and historical policy. It verifies the epoch signature, package commitment, opened secret ID and opening key. The opening and recovery identity keys sign a challenge for each package. The recovery identity and active device sign the digest of the complete list. Server verifies both per-package signatures, inclusion in the signed epoch, current admission and the exact set of generations. It records readiness in the same transaction, so a policy or generation change rejects the entire request.

After loss of all devices, the recovery identity and new signing key approve one replacement. A separate ECDH HMAC proves possession of the replacement device's recipient key. The challenge binds the current policy head and server cutover. The signed change preserves the profile, roles and restrictions, revokes old devices and sessions, and queues rotations. An archive task opens a recovery package only for an exact lease target and only with full history permission. For limited history a historical live package is delivered only when the current and historical continuous admission start at the same position.

After owner recovery, the new device signs scoped attestations v2. The original owner key remains pinned to genesis. A separate authority chain starts from that key: the current signer authorizes the recovery key, then the active recovery identity and new device approve a signer transition. Each transition binds the policy action and revision. Readers verify compact evidence and save the latest accepted head to detect known rollback. Historical v1 attestations retain their format. A new signer can attest a verified historical revision using its own authority proof.

New migration preparation commits the recovery identity to API 3 genesis. Client opens recovery packages from signed epochs and confirms coverage before cutover. Cutover approval also persists the initial authority in a detached certificate signed after the genesis and cutover digests are known. It binds the exact recovery key from the pinned snapshot. Earlier migration checkpoints retain their existing format.

Use an incompatible admission and storage boundary for protected mode. Before the cutover, a trusted client converts retained ciphertext and its references in maintenance with a verified backup and resumable checkpoints. The API 2 root and copies outside the migrated store remain usable for old ciphertext. API 2's successful admission data is written at invite confirmation in `memberships.joined_at` and `invite_redemptions`; verify eligibility and ordering on the source snapshot before choosing an owner. If the necessary ordering is ambiguous, report the affected migration instead of using profile creation order.

Live voice requires independent ephemeral secrets. Verify actual media publish and receive permissions, capacity and active participants. API 2 signs a 60-second LiveKit grant and removes active identities through RPC. Establish how a pre-existing grant behaves after disconnect, permission changes and expiry in the shipped LiveKit version before claiming G6. Manager remains on the host side of the boundary.

The synthetic AES-GCM probes in `tests/compatibility/protected-history.test.mjs` exercise G1 and G2 after an epoch transition. They model confidential recipient delivery with independent symmetric fixture keys. Public-key envelopes, canonical payloads, publication times, rollback, migration, retries and LiveKit are still open. No new production cryptography dependency is selected in this design.

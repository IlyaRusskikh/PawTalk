# Независимый выпуск релизов

[English](releasing.en.md) · [Индекс](README.ru.md)

Семейства тегов: `client-vX.Y.Z`, `server-vX.Y.Z` и `manager-vX.Y.Z`. У Windows и Linux Manager **один тег Manager**. Исходные манифесты задают версию кандидата; публичный релиз подтверждается лишь GitHub Releases и подписанными артефактами.

1. Подготовьте рабочую ветку от текущего `main`. Обновите версии соответствующего компонента, совместимость, двуязычные инструкции, историю изменений и [исходные описания релиза](../releases/README.ru.md). Текст должен быть корректным публичным описанием до и после выпуска, без неподтверждённых заявлений об успехе CI и временных «ожидает публикации».
2. Выполните нужные тесты компонента, проверки release notes, документации и ссылок; создавайте PR только с разрешения владельца. Для merge нужны успешный PR CI и отдельное решение владельца.
3. После merge отдельный **Release Candidate Preflight** проверяет точный неизменённый SHA `main` и готовит подписанные артефакты. Подготовка **не означает** создание тегов и публикацию.
4. Раздельные подтверждения тега и публикации продвигают **те же подготовленные байты** с проверкой подписи, хеша, immutable refs, канала, API/data schema и полного тела релиза. Ошибка не является разрешением скрыто заменить тег или бинарник.
5. После публикации каталог загрузок формируется из GitHub Releases; не определяйте «последнюю» версию по package manifest и не используйте общий `releases/latest`.

Скрипты публикации читают `releases/<tag>.md` как **канонический локальный двуязычный исходник публикации**, digest которого фиксируется для утверждённого кандидата. Он может отличаться от существующего публичного описания Release; см. [зафиксированные расхождения](../releases/README.ru.md). Человеческая локализация отделена от контракта подписанной публикации. Публичные описания не переписываются при очистке документации. [Тесты](../tests/release/release-notes.test.mjs) · [workflow](../.github/workflows/release.yml).

## Подготовка и продвижение кандидата

После merge запустите **Release Candidate Preflight** (`release.yml`) на `main`. В `components` укажите `client`, `server`, `manager`, набор через запятую без пробелов или `all`. По умолчанию `promote=false` выполняет выбранные нативные проверки, сборки и подписание, сохраняет готовые пакеты, receipts и `pawtalk-candidate-index`; тегов и публичных релизов не создаёт. Проверьте готовность, точный SHA, версии, каналы и digest артефактов. [Настройки GitHub и согласований](../agents/rules/github.md) задаёт владелец.

Если успешный prepare-only run уже есть на неизменённом текущем SHA `main`, предпочтителен **Promote Existing Preflight** (`promote-candidate.yml`) с его `source_run_id`. Он берёт полный исходный набор компонентов, версии и каналы из сохранённого index и проверяет исходный run/attempt, обязательные jobs, digest архивов, receipts, подписи и OCI digest. Повторять сборку, подписание или `check.yml` запрещено. Альтернатива — новый запуск `release.yml` с `promote=true`, выполняющий полную подготовку заново до согласований.

Оба пути требуют раздельных подтверждений **release-tag** и **release-publish**. Сохраните исходные артефакты до обоих согласований; срок хранения — семь дней с учётом ограничений репозитория. Изменённый SHA main, истёкшие/отсутствующие артефакты, другой source attempt, несовпадение версий/каналов, отсутствие index или существующие теги/релизы запрещают повторное использование. Не перезапускайте source jobs и не меняйте main/каналы во время согласования. Старые кандидаты без index требуют новой подготовки. [Модель продвижения и отказы](../agents/decisions/003-promote-existing-preflight.md).

Создание тегов и публикация GitHub/GHCR не атомарны между компонентами. При частичном сбое сообщите завершённые и неудачные этапы, сохраните диагностику и подготовьте новую версию/PR; не повторяйте вслепую и не заменяйте теги, файлы или образы. Каталог/Pages развёртывается только после успешной публикации; prepare-only не запускает deployment.

## Контракт описаний релизов (REL-NOTES-01…06)

- **REL-NOTES-01:** Полное описание для пользователя подготовлено до merge PR.
- **REL-NOTES-02:** Запрещены временные статусы публикации/CI: «ожидает публикации», «tag CI pending», «проверки будут выполнены» и аналоги на обоих языках.
- **REL-NOTES-03:** Нельзя заранее заявлять об успешной проверке или публикации.
- **REL-NOTES-04:** Источник результатов — GitHub Actions; ссылка на конкретный run необязательна и допустима только после подтверждения.
- **REL-NOTES-05:** Текст достоверен до, после и много позже публикации.
- **REL-NOTES-06:** Точность фактов RU/EN проверяется одинаково строго.

Каждый `releases/<tag>.md` хранит точный двуязычный текст для публикации. Нормализованный SHA-256 выбранного описания фиксируется в plan/receipt кандидата и не должен меняться между планом, тегом и публикацией. Три известных неудачных кандидата заморожены по хешам только для исторического сканирования; они не опубликованы и не освобождаются от проверки при выборе в кандидаты. Перед подготовкой запускайте `node tooling/ci/check-release-notes.mjs`, а для сравнения уже опубликованного текста — `node tooling/ci/check-release-notes.mjs --published <tag>` (только чтение). Изменение публичного текста требует **отдельного разрешения владельца** без изменения тега, файлов, подписей и digest.
